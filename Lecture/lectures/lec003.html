HTTP and the Raw API Call

Every SDK and framework in this course is a wrapper around one HTTP request. Make that request yourself once, and nothing later will feel like magic.

Overview

An LLM API is a web service. You send an HTTP POST with a JSON body describing the conversation, and get back a JSON body with the model's reply and some metadata. In this lecture we build that request piece by piece with httpx, a modern Python HTTP client.

PartValueWhy
MethodPOSTWe send data (the conversation).
URL{endpoint}/openai/v1/chat/completionsWhich resource and which operation.

Header Content-Typeapplication/jsonTells the server how to parse the body.

response = httpx.post(
    "https://my-resource.openai.azure.com/openai/v1/chat/completions",
    headers={"api-key": key, "Content-Type": "application/json"},
    json={"model": "gpt-4.1-mini", "messages": [{"role": "user", "content": "Hi"}]},
    timeout=60,
)
response.raise_for_status()      # 4xx/5xx -> httpx.HTTPStatusError
data = response.json()           # JSON text -> Python dict
print(data["choices"][0]["message"]["content"])

Anatomy of the response

{
  "id": "chatcmpl-...",
  "model": "gpt-4.1-mini-2025-04-14",
  "choices": [{
    "index": 0,
    "message": {"role": "assistant", "content": "A large language model is ..."},
    "finish_reason": "stop",
    "content_filter_results": { ... }        // Azure-specific
  }],
  "usage": {"prompt_tokens": 18, "completion_tokens": 31, "total_tokens": 49}
}
  • choices: a list because you can ask for several alternatives (n). Usually one.
  • finish_reason: stop (finished), length (hit a token limit), tool_calls, content_filter.
  • usage: tokens in and out. This is what you pay for (Lecture 004).

Goal

  1. Explain the four parts of an LLM API request: method, URL, headers, body.
  2. Send a chat completion with httpx and parse the JSON response.
  3. Read finish_reason and usage.
  4. Turn HTTP errors into exceptions with raise_for_status() and handle them.

Success Criteria

  • The script prints the full JSON response, then the reply, finish reason and usage
  • A wrong key produces a readable HTTP 401 message instead of a crash
  • All 6 checks pass (2 of them call the live API)

Walkthrough

  1. build_url: use endpoint.rstrip("/") so a trailing slash doesn't produce //openai.
  2. build_body: you wrote this in Lecture 002. Reuse the idea.
  3. send_chat: httpx.post(..., json=body) serializes the dict for you. Don't call json.dumps yourself.
  4. Run it and read the full JSON. Find content_filter_results: Azure screens every request and response.
Try the stretch goals Use a deployment name that doesn't exist (404). Add "temperature": 0 and run three times. Add "max_completion_tokens": 5 and look at finish_reason.

Common Pitfalls

Forgetting raise_for_status()

Without it, a 401 response is parsed as if it were a reply, and you get a confusing KeyError: 'choices' instead of a clear error.

No timeout

A request without a timeout can hang forever if the network stalls. Always set one.

Old URL formats in tutorials

Older Azure examples use /openai/deployments/{name}/chat/completions?api-version=…. The v1 path used here is simpler and OpenAI-compatible.

Discussion

If raw HTTP works, why use an SDK at all?

SDKs add typed responses, retries, timeouts, streaming parsers, file uploads and helpers such as structured output parsing. You'll appreciate each one more now that you've done without it.

Why is the model call a POST and not a GET?

The request carries a body (the conversation), it isn't cacheable, and it isn't idempotent: the same request can produce a different answer.
