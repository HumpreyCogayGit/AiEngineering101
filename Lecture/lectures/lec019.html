Embeddings and Similarity

"How do I get my money back?" and "refund policy" share no words but mean the same thing. Embeddings let a computer measure that, and most RAG systems use them to find the passages that answer a question.

Overview

Module 4 teaches Retrieval-Augmented Generation (RAG): at question time, retrieve the passages of your documents that are relevant, and give them to the model as context for its answer (the term comes from Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", 2020). Step one is semantic search, finding text by meaning rather than by keyword. An embedding model makes that possible by turning text into vectors.

Concept

Text → vector

client.embeddings.create(model="text-embedding-3-small", input=["You can return beans within 30 days."])
# -> [0.0123, -0.0456, 0.0789, ...]     1536 numbers

An embedding model is trained so that texts with similar meaning get vectors pointing in similar directions in a high-dimensional space. You can't interpret individual numbers; only distances between vectors carry meaning.

flowchart LR A["'How do I get my money back?'"] --> E[Embedding model] B["'Return beans within 30 days for a refund'"] --> E C["'Cold brew steeps 16 hours'"] --> E E --> V["vectors: A and B point the same way;
C points elsewhere"]

Cosine similarity

cos(θ) = (a · b) / (|a| × |b|)

 1.0  same direction    → closest in meaning
 0.0  perpendicular     → unrelated
-1.0  opposite
import numpy as np
def cosine_similarity(a, b):
    a, b = np.asarray(a), np.asarray(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

It ignores vector length and compares only direction. In practice, scores between related texts are often 0.3–0.7 rather than near 1. Compare scores against each other; don't rely on absolute thresholds.

Semantic search in three steps

  1. Index (once): embed every document chunk and store the vectors.
  2. Query (per question): embed the question with the same model.
  3. Rank: compute similarity to every stored vector and return the top k.

Step 3 is a brute-force loop here. Vector databases (Lecture 021) do it fast for millions of vectors.

Worked example: one query, from text to ranking

Follow the query "How do I get my money back?" through the three steps, with the numbers of a real run (text-embedding-3-small).

1. The query becomes a vector. 1,536 numbers; here are the first six:

[-0.0046, -0.0173, -0.0127, 0.0413, -0.0556, -0.0176, ...]      length (norm) = 1.0002

No single number means anything. The eight sentences were embedded the same way, once, into eight more vectors.

2. Cosine similarity against every stored vector. Eight dot products, one score per sentence:

0.285  You can return unopened beans within 30 days for a full refund.     ← no word in common with the query
0.199  Earn one reward star for every 50 pesos you spend.
0.076  Standard shipping is free for orders over 1,500 pesos.
0.064  Keep coffee beans in an airtight container away from light.
0.060  Cold brew should steep in the fridge for 16 to 18 hours.
0.058  Employees get 15 days of paid vacation per year.
0.018  Barako Bold is a strong, smoky dark roast from Batangas.
0.014  Our Makati café opens at 6:30 in the morning.

3. Sort and keep the top k. With k=2 the search returns the refund sentence and the rewards sentence.

Read the scores carefully, because they are not what most people expect:

  • The winner scores 0.285, not 0.9. A short question and a statement that answers it are related, not identical. What matters is that it is clearly ahead of the rest.
  • The gaps carry the information. From first to second the score drops by 0.09; from third to sixth by 0.02. The top two stand out, and everything from the third down is noise of about the same size.
  • The runner-up is wrong but understandable. "Money back" and "reward for every 50 pesos you spend" are both about money returning to a customer. Similar is not the same as relevant.
  • A threshold would have failed. "Keep everything above 0.5" returns nothing here; "above 0.05" returns six sentences. Rank, then let a later step judge.

On another embedding model the same query gives different numbers (often much higher ones) and usually the same order. That is why scores from two models cannot be compared, and why the ranking is the result you rely on.

Walkthrough

  1. Get an embedding model: on Azure, deploy text-embedding-3-small in Foundry and set AZURE_OPENAI_EMBEDDING_DEPLOYMENT; on Ollama, run ollama pull nomic-embed-text.
  2. embed_texts: one request for the whole list is far faster than one per text.
  3. Test cosine_similarity on tiny vectors first: [1, 0] vs [0, 1] should be 0.
  4. Add your own queries and sentences. Try a query in Filipino or Spanish: multilingual embedding models match across languages.

Common Pitfalls

Mixing embedding models

Vectors from different models (or different dimensions) are not comparable. Re-embed everything if you change models. The course's shared index includes the embedding model's name in its collection name for this reason, so switching provider builds a new index instead of mixing vectors.

Leaving out the prefixes an embedding model was trained with

Some open embedding models expect a task prefix on every text: nomic-embed-text wants search_query: before a question and search_document: before a passage, and ranks noticeably worse without them. aicourse.llm.get_embeddings() adds the prefixes configured in .env (OLLAMA_EMBEDDING_QUERY_PREFIX, OLLAMA_EMBEDDING_DOCUMENT_PREFIX). A raw client.embeddings.create() call sends exactly what you give it. Azure's text-embedding-3 models use no prefix.

Expecting keyword precision

Embeddings capture meaning, so they can miss exact codes like "BL-2026-0412" or rare names. Lecture 023 adds keyword search to cover this.

Embedding very long texts

One vector for a 20-page document blurs all its topics together. That's why we chunk (Lecture 020).

Discussion

Is "similar" the same as "relevant"?

No. "What is your refund policy?" is similar to "What is your shipping policy?", but it's not relevant to it. Similarity is a proxy for relevance, which is why retrieval needs evaluation (Lectures 023 and 024).

Where else are embeddings useful?

Duplicate ticket detection, clustering feedback by topic, recommendations ("customers who liked this…"), and routing questions to the right team.
