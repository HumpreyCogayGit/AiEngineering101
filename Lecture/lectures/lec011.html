Reliability

In production, API calls fail regularly: rate limits, timeouts, overloaded servers. Reliable apps expect failure and handle each kind appropriately.

Overview

A demo that works 99% of the time is impressive. A product that fails for 1 in 100 users is not. This lecture covers classifying errors, retrying the right ones with exponential backoff and jitter, logging, and running many calls concurrently without tripping rate limits.

Concept

Retryable vs permanent errors

ErrorSDK exceptionRetry?
429 Too Many RequestsRateLimitErrorYes, after waiting
TimeoutAPITimeoutErrorYes
Network failureAPIConnectionErrorYes
5xx server errorInternalServerErrorYes
400 bad request / content filterBadRequestErrorNo: the same request fails again
401 / 404AuthenticationError / NotFoundErrorNo: fix the configuration

Exponential backoff with jitter

attempt 1 fails → wait ~0.5 s
attempt 2 fails → wait ~1 s
attempt 3 fails → wait ~2 s       delay = min(cap, base × 2^(attempt-1)) + random jitter
attempt 4 fails → give up, raise

Why exponential? If the service is overloaded, hammering it makes things worse; backing off gives it room to recover. Why jitter? Without randomness, a thousand clients that failed together retry together and overload the service again (a "thundering herd").

The SDK already retries The openai client retries 2 times by default (max_retries). In this exercise we turn that off with with_options(max_retries=0) to build it ourselves. In real projects, configure the SDK's retries and timeouts rather than reinventing them, and use a library like tenacity for custom logic.

Concurrency with a limit

LLM calls spend most of their time waiting on the network, so running them concurrently with asyncio gives big speed-ups. Unlimited concurrency triggers 429s, so cap it with a semaphore:

semaphore = asyncio.Semaphore(3)            # at most 3 in flight

async def limited(prompt):
    async with semaphore:
        return await complete_one(prompt)

results = await asyncio.gather(*(limited(p) for p in prompts))   # keeps input order

Logging

Log each attempt, failure type, wait time, latency and token count, using logging rather than print, so production systems can collect, filter and alert on them. Lecture 035 builds full tracing.

Goal

  1. Classify API errors as retryable or permanent.
  2. Implement exponential backoff with jitter and a retry limit.
  3. Run calls concurrently with asyncio.gather and a semaphore.
  4. Make time-dependent code testable by injecting sleep.

Success Criteria

  • The retry demo logs two warnings, then succeeds
  • 6 prompts run concurrently (at most 3 in flight), noticeably faster than one after another, with results in input order
  • A ValueError is not retried; a RateLimitError is
  • All 5 checks pass (they run offline and instantly)

Walkthrough

  1. backoff_delay: compute the capped base delay, then add random.uniform(0, delay * 0.25).
  2. call_with_retry: loop over range(1, max_attempts + 1). In except retry_on, re-raise on the last attempt, otherwise sleep and continue.
  3. Only retry_on errors are caught, so anything else propagates immediately.
  4. complete_many: three lines, as shown above.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add a circuit breaker: after N consecutive failures, stop calling for a while and fail at once. Done when: during a simulated outage the later requests send nothing, and the first request after the cool-down closes the circuit again.

Common Pitfalls

Retrying everything

Retrying a 400 just repeats a failure (and costs money), and retrying non-idempotent actions can duplicate them, such as sending two emails.

Double retries

Your retries times the SDK's retries times a gateway's retries can turn one failure into dozens of calls. Retry at one layer.

time.sleep inside async code

It blocks the whole event loop. Use await asyncio.sleep().

Discussion

The model is down for 10 minutes. What should the user see?

Not a spinner for 10 minutes. Fail after a bounded time with a clear message, and consider fallbacks: a second region or deployment, a smaller model, or a cached answer.

Should you honour the Retry-After header?

Yes, when present. The server is telling you exactly how long to wait. The SDK does this automatically.
