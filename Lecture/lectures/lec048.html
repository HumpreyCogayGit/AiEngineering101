Release-Gated Evaluation

A one-line change to the system prompt can break a category nobody looked at. Make the evaluation a gate that every change passes before it ships.

Overview

Lecture 037 said the evaluation is the definition of done. So far it is a command someone has to remember to run. This lesson makes it part of the release process: every pull request is checked against an approved baseline, per category, and a regression blocks the merge.

Two problems make this harder than running unit tests in CI. Model answers vary between runs, and a live evaluation needs the provider's secrets, which pull requests (especially from forks) must not get. The lesson solves both with two modes: a deterministic replay on every pull request and a live run started by hand.

Concept

What is being released

The answers change when the prompt, the tools or the model change. So a release is identified by exactly those:

{"prompt_version": "p-6e59900d4803",          # sha256 of the system prompt, first 12 hex digits
 "tools_version":  "p-41c5bdffbd08+mcp:notes", # the same for the tool names and descriptions
 "model":          "gpt-5.6-sol"}

Treat prompts as versioned artifacts: the version is computed from the text, so nobody has to remember to bump it, and a baseline is meaningless unless it names the version it was measured with.

A baseline, and a comparison per category

baseline.json holds the per-category results of the last approved release, with who approved it and when. The gate compares a candidate with it:

SituationResult
Safety lost any casefail (no tolerance)
Another category lost more cases than the tolerancefail
A category fell below the capstone's bar (75%)fail
A category lost cases within the tolerancewarn
A category disappeared from the runfail: cases were dropped
A new categorywarn: nothing to compare with yet

The tolerance exists because live answers vary: the same release scored memory 4/4 in one run and 3/4 in the next while this lesson was written. Lecture 046's stretch goal 1 measures that spread; set the tolerance from it, and keep it at zero for categories where one failure is too many.

Replay on every pull request, live by hand

flowchart LR PR["pull request"] --> RP["replay: recorded replies
→ capstone score_case"] RP --> CHK{"prompt/tools same
as the recordings?"} CHK -->|no| F1["FAIL: re-record live"] CHK -->|yes| G1["gate vs baseline"] MAN["started by hand
(secrets)"] --> LV["live: real evaluation"] --> G2["gate vs baseline"] G1 & G2 --> REP["report uploaded
as an artifact"]

Replay feeds the recorded replies through the capstone's own scoring code. It is deterministic, free and needs no secrets, so it runs on every pull request. It catches changes to the evaluation cases and the scoring, and it refuses recordings made for another prompt or tool set: a pull request that changes what the model is asked must bring new recordings, made live.

Live runs the real evaluation with the provider's credentials, from a protected environment, started by hand before a release or on a schedule. GitHub Actions does not give secrets to workflows triggered from forks, which is one more reason the pull-request job must not need them (GitHub: using secrets).

replay:
  if: github.event_name == 'pull_request'
  steps:
    - run: uv run python EXER048/solution/release_gate.py gate --replay
    - uses: actions/upload-artifact@v7
      if: always()                     # the report matters most when the gate failed
      with: {name: release-gate-replay, path: EXER048/solution/output/release_gate.md}

Approval is a person's decision

A change that passes does not become the baseline by itself. Someone reads the report, runs release_gate.py approve --by <name>, and commits the new baseline.json and recordings.json with the change. The baseline's history in git is then the record of every quality decision.

The Project

You complete the prompt version, the comparison and the report in release_gate.py, and the two jobs of release-gate.yml. The baseline and the recordings were made live and are given.

Goal

  1. Identify a release by what changes its answers, with versions computed from the content.
  2. Compare a candidate with an approved baseline per category, with a stricter rule for safety.
  3. Run a deterministic gate on every pull request without secrets, and a live gate by hand.
  4. Keep a person in charge of approving a new baseline, with the report as the evidence.

Success Criteria

  • A prompt gets the same version id until its text changes; line endings do not matter
  • Safety fails on any drop; other categories fail beyond the tolerance or below the capstone's bar; a dropped category fails, a new one warns
  • The report shows both releases, marks what changed, has a row per category, and says how to approve a passing change
  • Replay reproduces the baseline from the recordings, and refuses recordings made for another prompt
  • The workflow replays on pull requests without secrets, runs live by hand with secrets, and uploads the report even when the gate fails
  • All 8 checks pass (offline)

Walkthrough

  1. prompt_version: normalize line endings, hash, shorten.
  2. compare: loop over the union of the categories; the order of the ifs is the table above.
  3. gate: the report is for a reviewer. Put the release table first: "what changed" is the first question.
  4. Run gate --replay, then edit one word of the capstone's system prompt and run it again (and undo the edit).
  5. Complete release-gate.yml; the check reads it as YAML. Copy it to .github/workflows/ in a repository of your own to see it run.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Take one prompt change through the gate: the baseline's memory category is 3/4 because the assistant refuses to use the conversation itself. Done when: replay refuses the changed prompt, the live gate passes with memory improved, and the report shows the new prompt version.
  2. Connect (EXER038). Add a trajectory category scored with the EXER038 functions. Done when: a simulated release with the same answers but four searches per question passes every answer category and fails the trajectory one.

Common Pitfalls

Gating on the overall pass rate

A release that fixes two grounding cases and breaks one safety case keeps the same average. Gate per category.

Secrets in the pull-request job

Workflows triggered from forks do not get repository secrets, so a live job on every pull request fails for outside contributors. Worse, a workaround that exposes secrets to forked code exposes them to anyone who opens a pull request.

Replaying stale recordings

If replay ignored the prompt version, a prompt change would pass by replaying the old prompt's answers. The version check turns that into a clear failure with instructions.

Approving automatically

A job that writes the new baseline whenever the gate passes slowly lowers the bar: each run within the tolerance becomes the next starting point. A person approves, and git keeps the record.

A baseline without a release identity

"Memory 3/4" means nothing without the prompt, tools and model it was measured with. Store them together.

Discussion

How large should the tolerance be?

Large enough that run-to-run noise does not fail good changes, small enough that a real regression does. Measure the spread of a few live runs of the same release, per category. Safety and anything with money keep a tolerance of zero.

The live evaluation takes two minutes and costs money. How often should it run?

Before every release, and on a schedule (nightly or weekly) to catch changes on the provider's side: a model version can change behind the same name. Replay covers every pull request for free.

What does the gate not catch?

Anything the cases do not cover. The gate protects what you measured; Lecture 049 is about finding what you did not.
