Operating Under Load

A service that accepts every request answers nobody well once enough of them arrive. Say no early, say when to come back, and stop cleanly.

Overview

The EXER042 service starts a thread for every request and lets each one run for up to 300 seconds. With ten users that is fine. With a thousand, every request waits for the same model provider, latency climbs for everyone, clients time out and retry, and the retries add more load. Lecture 011 covered the client side of this (retries, backoff, a concurrency limit on outgoing calls). This lesson covers the server side.

Three ideas carry the lesson: refuse cheaply before doing expensive work, tell clients when to come back, and measure from the user's side with percentiles and an objective. A fourth fixes the problem Lecture 041 left open: the service ignored SIGTERM.

Concept

Refuse early, in order of cost

flowchart LR R["request"] --> S{"body > 20 KB?"} -->|yes| E413["413"] S --> A{"token?"} -->|no| E401["401"] A --> D{"draining?"} -->|yes| E503a["503"] D --> L{"rate / budget?"} -->|over| E429["429 + Retry-After"] L --> Q{"free slot or
room in queue?"} -->|no| E503b["503 + Retry-After"] Q --> M["ask the model"] --> T{"in time?"} -->|no| E504["504"] T --> OK["200"]

Every check before "ask the model" costs microseconds. A request refused there costs the service almost nothing; a request that waits five minutes and then fails costs a thread, a connection, model tokens and the user's patience. The Google SRE book calls this handling overload: a fast, explicit rejection is better than a slow failure.

CodeMeaningClient should
413Content too largeNot retry; send less
429This client is over its limit (RFC 6585)Wait Retry-After seconds
503The service is busy or shutting downWait Retry-After, possibly try another replica
504No answer within the deadlineRetry later, with backoff

Retry-After turns a refusal into a schedule. Stretch goal 2 measures what happens when clients ignore it.

Two limits per user, one for the service

  • A rate limit counts requests. A token bucket allows a burst (5 at once) and then a steady rate (one every 3 seconds). Each user has their own bucket.
  • A budget counts cost. One user with long prompts can spend more tokens in ten requests than others in a thousand. A daily token budget per user caps the bill a single account can run up.
  • A concurrency limit protects the service. At most N questions run at once; at most M wait, each for a limited time. Beyond that: 503. The queue is bounded on purpose: an unbounded queue turns overload into unbounded latency.

Deadlines, and what a timeout does not stop

future = executor.submit(ask, question, key, principal)
future.add_done_callback(lambda _: admission.release())   # release when the work STOPS
reply = future.result(timeout=60)                          # 504 after 60 s

A Python thread cannot be killed. After the 504 the question keeps running, and keeps calling the model, until it finishes. So its slot is released when the work stops, not when the caller stops waiting; otherwise timed-out work piles up outside the limit. Real cancellation needs cooperation: an async task that can be cancelled, or a timeout passed down to the model client (Lecture 011).

Measure what users experience

An average hides the slow requests. Report percentiles: p50 is the typical user, p95 and p99 are the unlucky ones. Then state an objective: a service level objective (SLO) over a service level indicator (SLI).

SLI   share of requests that were answered within 2 s, or refused with a 4xx
SLO   SLI ≥ 95% over the measurement window
error budget = 1 − SLO = 5% of requests may be bad;  "used ×2.0" means twice that

A 429 counts as good here: the service did what it promised to that user. A 503 does not.

Graceful shutdown as process 1

Lecture 041 found that its service ignored docker stop: process 1 in a container gets no default signal handling, and the service installed no handler. The fix is a handler that drains:

def on_sigterm(signum, frame):
    def stop():
        shutdown.drain(grace)    # readiness → 503, new questions → 503, running ones finish
        server.shutdown()        # serve_forever() returns; main() exits 0
    threading.Thread(target=stop, daemon=True).start()   # NOT in the handler: see Pitfalls

signal.signal(signal.SIGTERM, on_sigterm)

Measured on the two images:

EXER041  docker stop -t 10  took 10.1 s, exit code 137 (killed)
EXER044  docker stop        took  0.4 s, exit code 0
         INFO helpdesk: SIGTERM: draining 0 request(s), up to 25 s
         INFO helpdesk: drained
         INFO helpdesk: stopped cleanly

The grace period of the service (25 s) must be shorter than the platform's (Docker: docker stop -t; Kubernetes: terminationGracePeriodSeconds, 30 s by default), or the platform kills it while it drains.

Goal

  1. Reject excess work early and cheaply, with the right status code and Retry-After.
  2. Limit each user by request rate and by token cost, and the service by concurrency and queue length.
  3. Enforce a deadline, and explain why a timed-out request still holds resources.
  4. Shut down gracefully on SIGTERM, including as process 1 in a container.
  5. Report latency percentiles and an SLO from a load test.

Success Criteria

  • Every refusal (413, 429, 503) happens before any model call, and 429 and 503 carry Retry-After
  • A question that misses the deadline gets 504, and keeps its slot until its work actually stops
  • On SIGTERM the process finishes the question in flight, answers new ones with 503, and exits 0
  • The load test prints throughput, p50/p95/p99, counts by status, and whether the SLO was met
  • All 9 checks pass (offline; one starts the service as a real process and sends it SIGTERM)

Walkthrough

  1. percentile, summarize, slo_report first: pure functions, quick to check.
  2. TokenBucket.take: refill by elapsed time, cap at the burst, take one. The check uses a fake clock.
  3. AdmissionControl.acquire: try for a free slot, then join the queue if there is room, then wait with a timeout.

Common Pitfalls

Calling server.shutdown() inside the signal handler

The handler runs on the main thread, which is inside serve_forever(). shutdown() waits for serve_forever() to return: the thread waits for itself, forever. Start a thread.

An unbounded queue

Requests are never refused; they wait. Latency grows without limit, clients time out and retry, and the queue grows faster. A bounded queue with a wait timeout turns that into quick 503s.

Releasing the slot on timeout

The caller got its 504, but the work is still running. Count it until it stops, or the limit no longer limits anything.

Failing liveness while draining

Readiness should fail (send no new traffic). Liveness should not: a failing liveness check makes the platform kill the process before the running requests finish.

Reporting the average latency

A mean of 0.8 s can hide 5% of users waiting 10 s. Report p95 and p99, and count refused requests separately from answered ones.

A tiny accept backlog

Before any of your code runs, the operating system queues new connections. Python's socketserver allows 5; a burst beyond that is reset. The service sets request_queue_size = 128.

Discussion

Where should the limits live when there are three replicas?

The concurrency limit protects one process, so it stays local. Per-user rate limits and budgets must be shared, or each user gets three times their limit: keep the counters in a shared store such as Redis, or enforce them in an API gateway in front of the replicas.

How do you choose the concurrency limit?

Measure. Find the point where throughput stops growing and latency starts climbing (stretch goal 1). That point is usually set by the model provider's rate limit or the GPU behind a local model, not by your service.

Why count a 429 as "good" in the SLO?

The SLO measures whether the service kept its promise. Refusing a user who is over their limit is the promise. If many well-behaved users get 429s, the limit is wrong, and that shows up as complaints and in a separate metric.
