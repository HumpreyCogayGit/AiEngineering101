Message Content Blocks

A message's content doesn't have to be a single string. It can be a list of typed blocks (text, images), which lets one message combine several kinds of input. And every block counts against the context window.

Overview

So far content has been a string. Modern chat APIs also accept a list of content blocks. You'll send an image to the model, then tackle the other side of the same coin: the context window, and how to keep a growing conversation inside it.

Concept

Content as a list of blocks

{
  "role": "user",
  "content": [
    {"type": "text", "text": "What shapes are in this picture?"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0KGgo...", "detail": "auto"}},
  ],
}
  • A string content is just shorthand for a single text block.
  • Images can be a public https:// URL or a data URL: data:<mime>;base64,<bytes>.
  • detail: low (cheap, low resolution), high (tiles the image, more tokens) or auto.
Base64 Encodes binary bytes as plain ASCII text so they can travel inside JSON. It makes data about 33% larger.

Images cost tokens

An image is turned into tokens too, from tens to over a thousand depending on size and detail. Resize large images before sending them; a phone photo at full resolution is wasted money.

The context window

Every model has a maximum context: system prompt + history + new input + output must fit. Even when it fits, very long contexts are slower and more expensive, and models can overlook details buried in the middle.

flowchart LR subgraph W["Context window (e.g. 128k tokens)"] S[system] --- H1[old turns ...] --- H2[recent turns] --- Q[new question] --- O[room for the answer] end

Strategies when history grows:

StrategyHowTrade-off
Trim (sliding window)Keep the system prompt and the newest N tokensSimple; forgets old facts
SummarizeReplace old turns with a model-written summaryKeeps the gist; costs a call, loses detail
RetrieveStore old turns or facts and fetch the relevant onesScales; more complex (Lectures 019 and 028)

The Project

content_blocks.py builds text and image blocks, asks the model about EXER006/images/shapes.png (a red circle, a blue square and a green triangle), and implements trim_history() to keep a 41-message conversation inside a 400-token budget.

uv run python EXER006/solution/content_blocks.py

Q: What shapes do you see, and what colour is each?
A: A red circle, a blue square, and a green triangle.

History: 41 messages -> trimmed to 11 to fit 400 tokens
First kept non-system message: Question number 15: blah blah

Captured from a real run. Your wording, numbers and timings will differ; the shape should match.

Goal

  1. Build messages with a list of content blocks.
  2. Send a local image as a base64 data URL.
  3. Explain the context window and the cost of images and history.
  4. Implement sliding-window trimming that keeps the system prompt.

Success Criteria

  • The model correctly describes the red circle, blue square and green triangle
  • A 41-message history is trimmed to fit 400 tokens, keeping the newest turns
  • All 7 checks pass

Walkthrough

  1. mimetypes.guess_type("shapes.png") returns ("image/png", None).
  2. base64.b64encode(...) returns bytes. Call .decode("ascii") to get a string for the URL.
  3. trim_history: walk the non-system messages with reversed(), keep each one while it fits the budget, then reverse the kept list back into original order.
  4. The check passes a count_fn that counts every message as 1 token, so you can reason about the expected result exactly.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Send two images in one message and ask for the differences (images/shapes_changed.png is the second image). Done when: the answer names the colour change, the missing triangle and the changed label.
  2. Connect (EXER005). Trim by summarizing the dropped turns into one message instead of deleting them. Done when: after trimming, the bot still knows an order number from the first turn, which plain trimming forgets.

Common Pitfalls

Splitting a turn when trimming

A naive trim can keep an assistant reply but drop the question it answered, or (with tools) drop a tool call but keep its result, which the API rejects. LangChain's trim_messages has options for this (Lecture 028).

Model without vision support

Not every model accepts images. gpt-4.1-mini and gpt-4o do. On Ollama, ollama show <model> must list the vision capability (gemma4:e4b has it).

Huge images

Requests have size limits, and big images cost many tokens. Resize to the resolution you need.

Discussion

With million-token context windows, why trim at all?

Cost and latency grow with every token you send, on every turn. Quality can also drop when relevant details are buried in a huge context. Big windows are a safety net, not a strategy.

When would you summarize instead of trim?

Long-running assistants where early facts matter (a customer's order number, preferences). Summaries keep them; trimming drops them.
