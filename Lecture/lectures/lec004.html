The SDK and Model Parameters

Swap hand-written HTTP for the official SDK, then learn the dials that shape every answer: tokens, temperature, output limits, and what they cost.

Overview

The openai Python SDK sends the same request you built in Lecture 003, but gives you typed objects, automatic retries, timeouts and streaming support. Despite its name it is the client library for the OpenAI-compatible API, whoever serves it: we point the SDK at Azure Foundry or at a local Ollama with one argument, base_url.

Concept

The client

from openai import OpenAI

client = OpenAI(
    base_url=settings.base_url,   # Azure: https://my-resource.openai.azure.com/openai/v1/
    api_key=key,                  # Ollama: http://localhost:11434/v1/
)
response = client.chat.completions.create(
    model=settings.chat_model,                  # Azure: deployment name. Ollama: e.g. "gemma4:e4b"
    messages=[{"role": "user", "content": "Hi"}],
)
response.choices[0].message.content             # attributes, not ["keys"]
response.usage.total_tokens

Tokens

Models don't read characters or words; they read tokens, chunks of text from a fixed vocabulary. In English a token is about ¾ of a word. Everything is measured in tokens: the context window, output limits, rate limits and price. You can count them locally with tiktoken:

import tiktoken
enc = tiktoken.get_encoding("o200k_base")    # GPT-4o / GPT-4.1; an estimate for other model families
enc.encode("hello world")                    # [24912, 2375]  -> 2 tokens
Tokenization surprises Numbers, code, rare words and non-English languages often use more tokens per word. "Kapeng barako" costs more tokens than "strong coffee".

Temperature: how the next token is chosen

At each step the model produces a probability for every possible next token. Temperature reshapes that distribution before sampling:

TemperatureBehaviourUse for
0 – 0.3Almost always picks the most likely token: focused, repeatableExtraction, classification, code, factual Q&A
0.7 – 1.0Balanced (1.0 is the default)Chat, writing
1.2 – 2.0More surprising choices, eventually incoherentBrainstorming, names

Even at temperature 0, outputs are not guaranteed to be identical across calls. Don't build systems that rely on exact repetition.

Two habits make your code work on both families:

  • Send an optional parameter only when the caller set it. ask() builds a kwargs dict and adds temperature and the output cap only when they are not None. Left out, the model's own default applies.
  • Treat a rejected parameter as an expected outcome. temperature_experiment() catches BadRequestError and records an empty list for a temperature the model refuses, instead of crashing halfway through.
From Lecture 008 on: model_params() Later exercises want temperature=0 for repeatable results. They write **model_params(temperature=0) (from aicourse.llm), which sends the parameter when your model accepts it and leaves it out when it does not. It finds out with one tiny test call, then remembers the answer in .aicourse_cache.json. You can also state it yourself with AICOURSE_SUPPORTS_TEMPERATURE=true|false in .env. The same helper takes max_tokens= and sends it under the name your provider applies.

Limiting output: max_completion_tokens / max_tokens

The API has two names for the output cap, and providers differ in which one they apply:

ParameterAzure FoundryOllama
max_completion_tokens (current name)Applied by every modelAccepted but ignored: the answer is not cut
max_tokens (original name)Classic models only; reasoning models reject itApplied

So that one line of code works everywhere, get_settings().max_tokens_param holds the right name for your provider: kwargs[settings.max_tokens_param] = max_tokens. A parameter that is silently ignored is worse than one that is rejected, which is one more reason to check finish_reason.

The cap limits how many tokens the model may generate. If it hits the cap, the answer is cut off mid-sentence and finish_reason is "length". Always check finish_reason before trusting an answer as complete.

Reasoning tokens count against the cap A reasoning model spends output tokens on thinking before it writes anything, and those hidden tokens are part of the cap (and of your bill). Local thinking models such as gemma4 behave the same way. With a small cap the whole budget can go to reasoning: you get finish_reason="length" and an empty answer. On these models, leave generous room, and read usage.completion_tokens_details.reasoning_tokens to see where the tokens went. The reasoning_effort parameter (none, low, medium, high) controls how much thinking happens. The course's helpers send it only when you set AICOURSE_REASONING_EFFORT in .env. Less thinking is faster and cheaper, but it costs quality: with none, a small local model picks tools noticeably worse (Module 3 and Module 5).

Cost

You pay per token, with different prices for input (prompt) and output (completion), quoted per million tokens:

cost = prompt_tokens × input_price / 1,000,000  +  completion_tokens × output_price / 1,000,000

Output tokens usually cost 3–5× more than input tokens. Long system prompts and long chat histories are paid again on every request.

The Project

Goal

  1. Create an SDK client for your provider with base_url and api_key.
  2. Explain tokens and count them with tiktoken.
  3. Use temperature and the output cap, and interpret finish_reason.
  4. Estimate the cost of a request from its usage.

Success Criteria

  • The script prints an answer, its token usage and an estimated cost
  • max_tokens=5 produces a cut-off answer with finish_reason="length" (on a reasoning model the text can even be empty: the budget went to hidden reasoning tokens)
  • On a classic model the answers are (nearly) identical at temperature 0 and vary at 1.0; on a reasoning model temperature 0 is reported as not supported and the script keeps running
  • All 7 checks pass

Walkthrough

  1. make_client(): take base_url and the key from get_settings(). Use .get_secret_value(), because the key is a SecretStr that hides itself when printed.
  2. ask(): pass temperature and the output cap (under the name in get_settings().max_tokens_param) only when they aren't None. Build a kwargs dict and unpack it with **kwargs.
  3. estimate_cost(): check your result by hand. 1M input tokens at $0.40 is $0.40.
  4. temperature_experiment(): wrap each temperature in try / except BadRequestError. Store an empty list when the message mentions temperature; re-raise anything else.
  5. Run the experiment several times. Notice how temperature affects variety, not quality.

Common Pitfalls

max_tokens vs max_completion_tokens

Newer hosted models use max_completion_tokens, and reasoning models reject the older max_tokens. Ollama is the reverse: it applies max_tokens and ignores the new name. Use get_settings().max_tokens_param instead of hard-coding either.

Reasoning models reject temperature

o-series and gpt-5 models return a 400 error for any temperature other than the default. Send the parameter only when it was asked for, and handle the 400 (see the table above). The course runs on both families.

Ignoring finish_reason

A JSON answer cut off by the length limit is invalid JSON. A summary cut off mid-sentence looks finished to a casual reader. Check it.

Discussion

Your model only accepts the default temperature. How do you get repeatable output?

With the prompt and the output format rather than the sampler: precise instructions, a closed list of allowed answers (Lecture 008), and structured output validated in code (Lecture 009). Those matter more than temperature on every model, which is why the later exercises still pass on a reasoning model.

Should you always use temperature 0 in production?

For extraction and classification, usually yes. For conversation, a little randomness sounds more natural. Pick per task, and evaluate (Lecture 024) rather than guess.

How would you cut the cost of a chatbot by half?

Shorter system prompts, trimming history (Lecture 006), a smaller model for easy turns, capping output length, and caching. Measure tokens per request first (Lecture 035).
