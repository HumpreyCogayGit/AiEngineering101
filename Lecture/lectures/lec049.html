Learning from Production

The evaluation set was written before anyone used the assistant. Real customers ask other questions, and most of them never press a thumbs-down.

Overview

Lecture 048 made the evaluation a gate. The gate protects what the cases cover and nothing else. This last lesson is about where new cases come from once the assistant is live: the traces it writes (Lecture 035), the feedback customers give, and a person who reviews a sample each week.

The loop is simple to draw and easy to do badly. Read only the thumbs-downs and you see a handful of complaints, some of them about the price of coffee. Read everything and nobody keeps it up. The lesson builds the middle path.

1. Explicit feedback is rare and noisy

In the four weeks of traces in this exercise, 68 of 291 answers were rated and 9 got a thumbs-down. Three of those were correct answers: the customer disliked the policy, not the answer. Explicit feedback is worth collecting, and it is not enough.

2. Implicit signals are common

What a customer does next says more than what they rate:

SignalHow to detect itWhat it suggests
Asked againNext message in the thread within a minute, sharing a content wordThe answer did not help
Asked for a person"human", "agent", "person" in the next messageThe customer gave up on the assistant
AbandonedNo further message after an answer that ended in a questionWeak on its own; combine with others

The signal belongs to the previous answer. "Can I talk to a human?" is not a failure to review; the answer before it is.

3. Review a sample, on purpose

The queue holds every thumbs-down and every implicit signal, plus a random sample of everything else, drawn with a fixed seed so two reviewers see the same queue. The random part matters: in this exercise it found a confidently wrong answer ("opened beans can be returned within 30 days") that no customer had flagged. Blocked attacks are left out; the guardrail report covers them.

4. A reviewed failure becomes a test

{"category": "grounding", "question": "Can I return opened beans?",
 "expect_keywords": ["14", "50%"], "expect_tools": ["search_knowledge_base"],
 "source": "production:t0010"}

The case uses the customer's own words, the EXER037 format, and a source that points back to the trace. Duplicates are removed: the same failure seen ten times is one case. The candidates are run against today's assistant (stretch goal 2) and then enter the gate with a new baseline (Lecture 048). This is the loop the course has been building towards: the evaluation set grows from what customers actually asked.

5. Watch for drift

Some problems are not one bad answer but a change in the whole distribution. Weekly metrics compared with the earlier weeks catch them:

week       questions  thumbs-down  refusals  p95 s
2026-W43         73           0%        0%   3.92
2026-W44         64          12%        0%   3.87
2026-W45         68          11%        0%   3.76
2026-W46         67          31%       24%   6.09
ALERT 2026-W46: refusal_rate 0.239 vs 0 before
ALERT 2026-W46: p95_seconds 6.09 vs 3.85 before

In the last week the assistant started answering "I don't know" to shipping questions (in the story, a re-index lost shipping.md) and got slower. No single trace shows that; the weekly refusal rate does. The same comparison works for cost: mean tokens per question rising after a release is a regression the answer-based gate cannot see.

A model can help triage Stretch goal 1 lets a model propose a verdict for each queued trace with the documents in view, and compares it with the person's verdicts. Treat it like any judge (Lecture 024): count the failures it calls "ok", because those never reach a person.

The Project

You complete the signals, the queue, the conversion to cases, deduplication, weekly metrics and drift alerts in feedback_loop.py. The traces and a person's reviews of the queue are given.

Goal

  1. Collect explicit feedback and derive implicit signals from what customers do next.
  2. Build a review queue that combines flagged traces with a reproducible random sample.
  3. Turn reviewed failures into deduplicated evaluation cases that feed the release gate.
  4. Detect drift in quality, latency and cost by comparing weeks.

Success Criteria

  • A request for a person, or the same question again within a minute, marks the previous answer
  • The review queue holds every thumbs-down and every signal, plus a reproducible random sample, and no blocked attacks
  • A reviewed failure becomes a case in the EXER037 format that its score_case accepts; duplicates are dropped
  • Weekly metrics show the thumbs-down rate, refusal rate, tokens and p95 latency per ISO week
  • The drift in the last week (refusals and latency) raises alerts; the quiet weeks do not
  • All 7 checks pass (offline)

Walkthrough

  1. implicit_signals: group by thread, walk pairs of consecutive messages, label the first of each pair.
  2. sample_for_review: filter, flag, then sample the rest with random.Random(seed), not the global random.
  3. to_eval_case and dedupe: small, but they decide what the gate will test for years.
  4. weekly_metrics and drift_alerts: ISO weeks from isocalendar(); each week against the mean of the earlier ones.
  5. Run the script and read the queue as a reviewer would. Which verdicts in reviews.json would you change?

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Let a model pre-triage the review queue with the documents in view, and compare it with the person's verdicts. Done when: the script prints the agreement and, separately, the failures the model called "ok".
  2. Connect (EXER048). Run the new candidate cases against today's assistant before they enter the gate. Done when: each case is reported as failing today (a live bug) or passing (a guard against a return).

Reference code, for after you have tried: EXER049/stretch/

Common Pitfalls

Reviewing only thumbs-downs

Most failures are never reported, and some reports are not failures. A random sample is how you find the first kind.

Adding cases straight from feedback, without review

A thumbs-down on a correct answer becomes a test that expects a wrong one. A person decides the verdict and the expected keywords.

Personal data in new cases

Cases are committed to the repository and read by everyone. Build them from the redacted traces (Lecture 047), and read each question once more before it is added.

Comparing a week with the week before only

One noisy week makes the next look like an improvement or a regression. Compare with the mean of several earlier weeks.

An unseeded sample

Two reviewers, or the same reviewer running the script twice, get different queues and cannot compare notes.

Discussion

How many traces should a person review each week?

Enough to find new failure types, few enough that it actually happens: often 20–50. Watch what the random part finds. If it keeps finding failures nothing flagged, the signals are missing something; if it finds nothing for weeks, shrink it.

A drift alert fires. What do you check first?

What changed that week: a deploy (the gate's report names the release), a re-index of the documents, a model version at the provider, or a new kind of customer question. The traces of the alert week, filtered by the metric, usually show which.

When is the loop "done"?

Never, and that is the point. The evaluation set, the gate and the review queue together are how an AI feature keeps working after launch: each failure found once is tested forever.
