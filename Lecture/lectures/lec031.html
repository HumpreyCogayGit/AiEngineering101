Multi-Agent Systems

Split work across specialist agents coordinated by a supervisor, and learn when that's worth the cost: on this lecture's task the supervisor team made 11 model calls where a two-agent handoff made 3.

Overview

One agent with twenty tools and a two-page system prompt picks tools less reliably, and every call pays for all of them. A common response is to split it: specialist agents with focused prompts and tools, and a coordinator that routes work between them. LangGraph makes each specialist a subgraph and the coordination a graph.

Concept

The supervisor pattern

flowchart LR S((START)) --> SUP{supervisor} SUP -->|research| R[researcher
agent + search tool] SUP -->|write| W[writer
agent, no tools] R --> SUP W --> SUP SUP -->|FINISH| E((END))
class Route(BaseModel):
    next: Literal["researcher", "writer", "FINISH"]
    instruction: str                  # what the chosen worker should do

def supervise(state):
    if len(state["steps"]) >= MAX_STEPS:          # hard stop in code
        return {"next": "FINISH", ...}
    route = llm.with_structured_output(Route).invoke([SystemMessage(SUPERVISOR_PROMPT)] + state["messages"])
    if route.next == "FINISH" and "writer" not in state["steps"]:   # invariant in code
        return {"next": "writer" if "researcher" in state["steps"] else "researcher", ...}
    return {"next": route.next, "instruction": route.instruction}
Prompts ask, code guarantees The supervisor prompt says "choose FINISH only after the writer has replied". Some models still finish as soon as the research reads like an answer, and the customer gets bullet points instead of a reply. Any rule that must hold on every run (an order of steps, a step limit, a permission) is checked in code. The prompt is there to make the right choice likely; the code is there to make the wrong one impossible.

Workers as subgraphs

Each worker is a full agent (create_agent) with its own prompt and tools. A wrapper node runs it on the shared conversation plus the supervisor's instruction, and adds only the worker's final message back to the shared state, named after the worker. Its internal tool calls stay private, which keeps the shared context small.

Handoffs: passing control without a coordinator

In the supervisor pattern every worker reports back, so each step costs an extra model call just to decide what happens next. With a handoff, the agent that is working names its successor itself. In LangGraph a node does that by returning a Command, which carries a state update and the next node:

from langgraph.types import Command

def research(state) -> Command:
    result = researcher.invoke({"messages": state["messages"]})
    used_search = any(isinstance(m, ToolMessage) for m in result["messages"])
    note = AIMessage(content=result["messages"][-1].text, name="researcher")
    return Command(
        goto="writer" if used_search else END,        # the handoff decision
        update={"messages": [note], "steps": ["researcher"]},
    )

builder.add_node("researcher", research, destinations=("writer", END))   # no conditional edge needed
flowchart LR S((START)) --> R[researcher] R -->|"Command(goto=writer)"| W[writer] R -->|nothing to research| E((END)) W --> E

A Command replaces the conditional edge: routing moves from the graph definition into the node. That is convenient, and also why handoff systems get hard to follow as they grow. Declare destinations so the graph can still be drawn and reviewed.

When not to use multi-agent

Multi-agent is expensive Every hop is another LLM call: supervisor, worker, supervisor, worker, supervisor. In the worked example below the supervisor team read about 13,000 input tokens where the handoff team read about 1,700, and failures become harder to debug. Try first: a better prompt, fewer tools, a fixed workflow (Lecture 026), or one agent with good tools. Choose multi-agent when tasks need separate tools, permissions or context.

Six rows, and the last column tells the story of the pattern:

  • The supervisor adds no messages. Its three rows change only next and instruction. It reads the conversation and writes a decision.
  • Each worker adds exactly one message. The researcher called its search tool to get there. None of those calls or results are in the shared list: the wrapper node returned only the final text, named researcher. The writer saw the researcher's bullet points, not the raw search results.
  • The instruction is not in the shared list either. It was given to the worker as an extra message for that one call and then dropped. The shared conversation stays the customer's email plus the two results.
  • steps is what the code checks. In the last row the supervisor said FINISH, and the guard looked at steps: writer is there, so the run may end. Had the model said FINISH in the fourth row, the same guard would have replaced it with writer.

Count the model calls behind the six rows: three for the supervisor, one or more for the writer, and several for the researcher (one per search round, plus its summary). In another run of the same request, measured with the tracker of Lecture 035, the supervisor sent the researcher out twice: that team made 11 model calls and read about 13,000 input tokens, while the handoff team made 3 calls and read about 1,700. The supervisor's rows are the difference: every routing decision re-reads the whole conversation, and a second research round is only one decision away.

The handoff version of the same request has two rows: researcher, then writer. Nobody decides in between.

Goal

  1. Build a supervisor that routes with structured output.
  2. Wrap specialist agents as nodes that share only their final output.
  3. Bound multi-agent loops with a step limit, and enforce ordering rules in code.
  4. Pass control directly between agents with Command (a handoff).
  5. Judge when multi-agent is worth the cost.

Success Criteria

  • The trace shows supervisor decisions and each worker's output
  • The final reply answers both questions (broken grinder, dog) from the documents
  • A supervisor that never says FINISH is stopped by MAX_STEPS, and one that says FINISH too early is sent back to the missing worker
  • The handoff team produces the same reply in fewer steps
  • All 10 checks pass

Walkthrough

  1. Create both sub-agents with create_agent(..., name=...). The writer has no tools.
  2. supervise: check the step limit first, then ask the router, then apply the guard: no FINISH before the writer has replied.
  3. The worker wrapper appends a HumanMessage with the instruction for the sub-agent only, and returns only an AIMessage(name=...).
  4. build_handoff_team: the same two agents, each node returning Command(goto=..., update=...).
  5. Count the LLM calls in both versions, then estimate the cost compared with a single agent.

Common Pitfalls

Sharing every internal message

If workers dump all their tool calls into shared state, context explodes and the supervisor gets confused. Share results, not process.

Ping-pong

The supervisor sends work back and forth endlessly. Clear "FINISH" criteria in the prompt plus a hard step limit fix it.

Workers that do each other's jobs

A researcher that writes the final email makes the writer redundant. Make the boundaries explicit in each prompt.

Discussion

Could this task be done by one agent?

Almost certainly, and more cheaply. That's worth saying out loud. The pattern pays off when workers need different permissions (a writer that can't touch the database), different models, or very different instructions.

How would you evaluate a multi-agent system?

End to end (is the final reply correct?) and per worker (is the research complete? is the writer faithful to it?). Traces (Lecture 035) are essential.
