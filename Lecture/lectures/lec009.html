Response Formatting

Programs need data, not prose. Learn the three levels of output control, from "please reply in JSON" to output that is guaranteed to match your schema.

Overview

Many AI features are really extraction: turn an email into an event, an invoice into line items, a ticket into a label. The output feeds code, so it must be machine-readable and correct in shape. This lecture compares three approaches and when to use each.

JSON mode

response = client.chat.completions.create(
    model=..., **model_params(temperature=0),
    messages=[{"role": "system", "content": "Extract the event. Respond in JSON with keys title, date, ..."},
              {"role": "user", "content": email}],
    response_format={"type": "json_object"},     # the word "JSON" must appear in the messages
)
data = json.loads(response.choices[0].message.content)

Structured outputs with Pydantic

class Event(BaseModel):
    title: str = Field(description="Short name of the event")
    date: str = Field(description="Date in ISO format YYYY-MM-DD")
    start_time: str | None = Field(description="24h time HH:MM, or null if unknown")
    attendees: list[str]

completion = client.chat.completions.parse(model=..., messages=..., response_format=Event)
event = completion.choices[0].message.parsed     # an Event instance, not a dict
if completion.choices[0].message.refusal: ...    # the model may refuse unsafe requests

The SDK converts your Pydantic model to a strict JSON Schema. The service uses constrained decoding: at each step only tokens that keep the output valid against the schema are allowed. The shape is guaranteed; the values still come from the model and can be wrong.

Descriptions are prompts Field(description=...) is sent to the model as part of the schema. "Date in ISO format YYYY-MM-DD" is how you get 2026-03-14 instead of "Saturday 14 March".
…but not on every provider Azure shows the schema, descriptions included, to the model. Ollama uses the schema only to constrain the shape of the output: the model never reads your descriptions, and answers "Saturday 14 March 2026" in a perfectly valid string field. Code that must run on both states the rules about values in the prompt as well: "Write dates as YYYY-MM-DD and times as 24-hour HH:MM." Keep the descriptions too. They cost nothing and document the schema.

Validate and repair

When you can't use structured outputs (some models, complex validation rules), validate the reply yourself and send the error back:

flowchart LR A[Ask for JSON] --> B{Pydantic validates?} B -- yes --> C[Return object] B -- no --> D[Append reply + error message] --> E{attempts left?} E -- yes --> A E -- no --> F[Raise]

Pydantic's error messages are precise ("date: Field required"), and models are good at fixing their output when shown them.

The Project

An event extractor for a messy email. All three methods should produce title, date = "2026-03-14", start_time = "09:30", a location and the list of attendees.

3) Validated with repair loop:
   title='Q2 Planning Workshop' date='2026-03-14' start_time='09:30' location='Makati office, 12th floor boardroom' attendees=['Maria', 'Jun', 'Priya', 'Ken']

Captured from a real run. Your wording, numbers and timings will differ; the shape should match.

Goal

  1. Use JSON mode and parse the result.
  2. Use structured outputs with a Pydantic model via chat.completions.parse.
  3. Implement a validate-and-repair loop with a retry limit.
  4. Choose the right level of output control for a task.

Success Criteria

  • All three methods extract the date as 2026-03-14
  • extract_structured returns a real Event object, not a dict or string
  • The repair loop recovers from a reply that is missing fields, and gives up after max_attempts
  • All 6 checks pass

Walkthrough

  1. JSON mode: the request fails if the word "JSON" doesn't appear in your messages. The given system prompt contains it.
  2. parse() works like create(), but returns .parsed.
  3. Repair loop: copy the messages first (list(messages)) so you don't modify the caller's list. The check verifies this.

Common Pitfalls

Structured output from a local thinking model

With thinking switched on, some local models (gemma4 on Ollama) intermittently answer a schema request with plain text, which fails to parse. The course sends reasoning_effort="none" to Ollama through model_params() and get_chat_model() for this reason. Change it with AICOURSE_REASONING_EFFORT in .env.

Trusting values because the shape is right

A schema guarantees date is a string, not that it's the right date. Add business validation (Lecture 014) and evaluation.

Strict-schema limitations

Strict mode needs every field listed as required (optional fields become X | None) and doesn't support every JSON Schema feature. Keep schemas simple.

Truncated JSON

If finish_reason == "length", the JSON is cut off. Raise the output limit or simplify the schema.

Discussion

Should date be a datetime.date instead of a str?

Pydantic can parse an ISO string into a date for you, which adds validation. The trade-off is stricter failure on odd inputs. Both are reasonable; decide what the rest of your code needs.

How do you represent "unknown"?

Make the field nullable and say so in its description ("or null if unknown"). Otherwise the model will invent a plausible value to satisfy the schema.
