An Agent from Scratch

An agent is a loop: think, act, observe, repeat. In LangGraph that's two nodes and one conditional edge, and once you've built it yourself, every agent framework becomes readable.

Overview

You've written the tool loop with the raw SDK (016) and used create_agent (017). Now you build the same agent as an explicit graph. This gives you a place to add custom behaviour (approval, memory, routing), which the next lectures do.

Concept

The ReAct loop

Reason + Act: the model reasons about the task, acts by calling tools, observes the results, and repeats until it can answer.

flowchart LR S((START)) --> A[agent
model with tools] A -->|tool_calls| T[tools
ToolNode] T --> A A -->|no tool_calls| E((END))
def agent(state: MessagesState) -> dict:
    response = llm_with_tools.invoke([SystemMessage(SYSTEM)] + state["messages"])
    return {"messages": [response]}                 # appended by the MessagesState reducer

def should_continue(state: MessagesState) -> str:
    return "tools" if state["messages"][-1].tool_calls else END

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(TOOLS, handle_tool_errors=True))
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue, ["tools", END])
builder.add_edge("tools", "agent")                  # ← the loop

Design notes

  • System prompt outside state: it's added at call time, so it isn't stored in the conversation and can change between runs.
  • ToolNode runs every requested tool (in parallel when there are several) and returns ToolMessages. With handle_tool_errors=True, exceptions become error messages the model can react to, instead of crashing the run.
  • Recursion limit: each node execution is a "step". Invoke with {"recursion_limit": 12}; exceeding it raises GraphRecursionError, your guard against runaway loops (and runaway bills).

The Project

A Nimbus Coffee assistant with three tools (calculator, lookup_product, current_time) built as an explicit graph, streamed step by step, with a recursion limit.

Goal

  1. Explain the ReAct loop and map it to a graph.
  2. Build an agent with MessagesState, a model node, a ToolNode and a conditional edge.
  3. Protect the loop with a recursion limit and tool error handling.
  4. Read a step-by-step trace of an agent run.

Success Criteria

  • The script prints each step: tool calls, tool results and the final answer
  • The order total (₱2,210) is computed by tools, not by the model's mental math
  • A model that never stops calling tools is halted by the recursion limit
  • All 6 checks pass

Walkthrough

  1. should_continue first. Use getattr(last, "tool_calls", None), because not all message types have that attribute.
  2. Build the graph exactly as in the diagram.
  3. run: catch GraphRecursionError and return a polite message.
  4. Compare your graph's Mermaid output with create_agent(...).get_graph().draw_mermaid().

Common Pitfalls

Forgetting tools → agent

The run ends after the tools execute and the model never sees the results.

Binding tools to the model but not to the ToolNode (or vice versa)

The model requests a tool the node doesn't have. Use the same list for both.

Very high recursion limits "to be safe"

A stuck agent at limit 1000 burns money. Set the lowest limit that fits your hardest legitimate task.

Discussion

How does the model know when it's done?

It decides: when it replies without tool calls, the loop ends. That's flexible but not guaranteed, which is why the recursion limit exists.

When would you replace the free loop with a fixed workflow?

When the steps are always the same (look up, then compute, then answer). Fixed graphs are faster, cheaper and more predictable. Agents shine when the path genuinely depends on intermediate results.
