Prompt Engineering Basics

A prompt is a specification. Vague specs give vague results. A few techniques fix most problems, and you should measure the result rather than trust your impression.

Overview

We build a support-ticket classifier three times. Version 1 is the prompt most people write first. Version 2 adds clear instructions, definitions, delimiters and an output format. Version 3 adds examples. A labelled dataset tells us which version is actually better. This "change, then measure" loop is the core skill of AI engineering.

Concept

Techniques that matter most

TechniqueExampleWhy it helps
Role and task"You are a support-ticket classifier."Sets context and expectations.
Explicit options with definitions"billing: payments, refunds, invoices …"Removes guesswork at the boundaries between categories.
Output format"Reply with the category name only, lowercase."Makes the output parseable by code.
Delimiters<ticket> … </ticket>Separates instructions from data, and helps against injection (Lecture 036).
Few-shot examplesuser/assistant pairs showing input → labelShows the task instead of only describing it. Very effective for format and edge cases.
Low temperature**model_params(temperature=0)Consistent outputs for classification. model_params leaves the parameter out on models that reject it (Lecture 004).

Few-shot as messages

messages = [
    {"role": "system", "content": SYSTEM_V2},
    {"role": "user", "content": "<ticket>My refund hasn't arrived.</ticket>"},
    {"role": "assistant", "content": "billing"},          # an example answer
    {"role": "user", "content": "<ticket>Images don't load in the app.</ticket>"},
    {"role": "assistant", "content": "technical"},
    {"role": "user", "content": f"<ticket>{real_ticket}</ticket>"},   # the real one
]

Measure, don't vibe-check

flowchart LR A[Write / change prompt] --> B[Run on labelled dataset] B --> C[Accuracy + look at failures] C --> A

Trying three examples by hand tells you little. A dataset of even 16 labelled cases shows real differences. Keep two rules:

  • Never put test cases in the prompt. If your few-shot examples come from the test set, the accuracy score measures memorization, not skill.
  • Read the failures. The ones it gets wrong tell you which definition to sharpen.

Normalizing outputs

Even good prompts sometimes produce "Billing." instead of "billing". Your code should be tolerant: lowercase, strip punctuation, and map unexpected answers to "unknown" rather than crashing. Lecture 009 removes this problem with structured outputs.

The Project

Three prompt builders (v1, v2, v3) for the labels billing, technical, account and other, a classify() function and an evaluate() loop over EXER008/tickets.json. The output looks like this (illustrative numbers; yours will differ):

v1 naive         accuracy = low      ← often answers with a sentence, not a label
v2 instructions  accuracy = much higher
v3 few-shot      accuracy = highest, usually ≥ 80%

Goal

  1. Write prompts with a role, definitions, an output format and delimiters.
  2. Add few-shot examples as user/assistant message pairs.
  3. Evaluate prompt versions on a labelled dataset and compare accuracy.
  4. Normalize model output into a fixed label set.

Success Criteria

  • The script prints accuracy for v1, v2 and v3
  • v1 often answers with a sentence instead of a label (accuracy is low)
  • v3 reaches at least 80% accuracy
  • Your few-shot examples do not appear in the test set
  • All 7 checks pass

Walkthrough

  1. Run v1 first and read its raw answer at the end of the output. That's why format instructions matter.
  2. Write SYSTEM_V2 as a multi-line string. Define each label by what belongs in it.
  3. Write 4 examples of your own (one per label) for v3.
  4. If accuracy is low, print the misclassified tickets and refine the definitions.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add a fourth prompt version that gives a one-sentence reason before its label, and measure it. Done when: the script prints the accuracy of v4 next to v3, with the reason for every miss.
  2. Connect (EXER024). Print a confusion matrix (expected label against predicted label), not only accuracy. Done when: you can read from the table which label is mistaken for which.

Reference code, for after you have tried: EXER008/stretch/

Common Pitfalls

Overfitting the prompt to the test set

Tweaking until a specific failing ticket passes can make others fail. Keep a held-out set if you iterate a lot.

Contradicting instructions

"Be detailed" plus "answer in one word". Models handle conflicts unpredictably. Re-read your prompt as a stranger would.

Ambiguous labels

"I can't log in to pay my invoice": account or billing? Decide the rule and write it into the prompt.

Discussion

Is prompt engineering a temporary skill that better models will make obsolete?

The tricks change; the core doesn't. Clear specifications, examples and measurement matter for people too. What gets less important over time is wording superstition.

When should you stop prompting and try something else?

When accuracy plateaus. Next steps are structured outputs, retrieval of better context (RAG), a bigger model, or splitting the task into steps.
