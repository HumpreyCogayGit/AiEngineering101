LangGraph Basics

Chains run in a straight line. Real workflows branch, loop and pause. LangGraph models them as a graph of steps that share state.

Overview

LangGraph is LangChain's library for stateful, controllable workflows and agents. create_agent from Lecture 017 is itself a LangGraph graph. Before adding LLMs, we learn the mechanics with plain Python functions: a support-ticket router with no model at all.

Concept

Three building blocks

BlockWhat it isIn code
StateA typed dict shared by all nodesclass TicketState(TypedDict): ...
NodeA function: reads state, returns a partial updatedef classify(state) -> dict
EdgeWhat runs next: fixed, or decided by a router functionadd_edge / add_conditional_edges
def classify(state: TicketState) -> dict:
    ...
    return {"category": "billing", "steps": ["classify"]}     # only the keys that change

def route_by_category(state: TicketState) -> str:
    return state["category"]                                 # the NAME of the next node

builder = StateGraph(TicketState)
builder.add_node("classify", classify)
builder.add_edge(START, "classify")
builder.add_conditional_edges("prioritize", route_by_category)
graph = builder.compile()
graph.invoke({"ticket": "I was charged twice!"})

Reducers: how updates merge

By default a node's update replaces the key's value. A reducer changes that:

steps: Annotated[list[str], operator.add]     # updates are APPENDED: ["classify"] + ["prioritize"] + ...

That's how MessagesState works: its messages key has a reducer that appends new messages (and replaces messages with the same id).

The graph we build

flowchart LR S((START)) --> C[classify] --> P[prioritize] P -->|billing| B[billing] P -->|technical| T[technical] P -->|general| G[general] B & T & G -->|high| E[escalate] --> X((END)) B & T & G -->|normal| X

Seeing inside

  • graph.get_graph().draw_mermaid() prints a diagram of your graph.
  • graph.stream(input, stream_mode="updates") yields each node's update as it happens, which is ideal for progress displays and debugging.

Why graphs instead of plain Python?

For a ticket router, plain if statements would do. Graphs earn their keep with what's coming next: loops with tools (027), persistence and resuming (028), pausing for humans (029), and streaming every step. All of these come from the framework.

The Project

A ticket router: keyword classification, priority detection, a handler per category, and escalation for urgent tickets. The steps list records the exact path each ticket took.

Goal

  1. Define typed state and nodes that return partial updates.
  2. Use a reducer to accumulate values across nodes.
  3. Route with conditional edges.
  4. Visualize a graph and stream node updates.

Success Criteria

  • The script prints a Mermaid diagram of your graph
  • steps shows the exact path each ticket took
  • Urgent tickets pass through escalate; normal ones don't
  • All 6 checks pass (offline)

Walkthrough

  1. Add the steps reducer, then implement classify and prioritize.
  2. Routers return node names; for the end, return END.
  3. Wire edges exactly as in the diagram, then paste your printed Mermaid into mermaid.live and compare.
  4. Extension: replace keyword classify with an LLM using structured output. The graph doesn't change at all.

Common Pitfalls

Returning the whole state from a node

With a reducer, returning the full steps list appends it again and doubles it. Return only what changed.

Mutating state in place

state["steps"].append(...) bypasses LangGraph and breaks persistence and streaming. Return updates instead.

Router returns a name that isn't a node

The run fails at that point. Annotate routers with Literal[...] so the graph knows the possible destinations.

Discussion

Which decisions should be code, and which LLM?

Use code when rules are clear and testable (priority keywords, thresholds); use an LLM when judgment over language is needed. Graphs make mixing both natural, with a deterministic skeleton and LLM decisions where they add value.

"Workflow" or "agent"?

A workflow has paths you designed; an agent's path is chosen by the model at runtime. Prefer workflows when you can: they're predictable, cheaper and easier to test. Use agent loops where flexibility is genuinely needed.
