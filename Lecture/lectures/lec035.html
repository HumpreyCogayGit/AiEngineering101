Observability and Cost

An agent run is a tree of model calls and tool calls. If you can't see it, you can't debug it, speed it up, or afford it.

Overview

"The agent gave a weird answer" is impossible to fix without knowing what happened: which tools it called, with which arguments, what came back, how long each step took, and how many tokens it used. That's observability. We build a tracer with LangChain callbacks, then look at hosted options.

Concept

Traces and spans

A trace is one run (one user question). It's made of spans: timed steps such as a model call or a tool call, each linked to its parent by a run id.

Trace: "What is the refund window, and is shipping free?"
├─ LLM  gpt-4.1-mini   0.84s  in=412  out=38   → calls search_kb, search_kb
├─ TOOL search_kb      0.21s  {'query': 'refund window unopened beans'}
├─ TOOL search_kb      0.19s  {'query': 'free shipping'}
└─ LLM  gpt-4.1-mini   1.32s  in=1288 out=96   → answer
Totals: 2 LLM calls, 2 tool calls, 1,834 tokens, $0.0008, 2.6s

Notice the second model call's input: the tool results made it three times bigger. Traces make costs like that visible.

Callbacks

class UsageTracker(BaseCallbackHandler):
    def on_chat_model_start(self, serialized, messages, *, run_id, parent_run_id=None, **kw): ...
    def on_llm_end(self, response, *, run_id, **kw):          # usage_metadata lives here
    def on_tool_start(self, serialized, input_str, *, run_id, **kw): ...
    def on_tool_end(self, output, *, run_id, **kw): ...
    def on_tool_error(self, error, *, run_id, **kw): ...

agent.invoke(inputs, {"callbacks": [tracker]})    # propagates to every nested model and tool call

Pass the handler in the run config and LangChain calls it for every nested step automatically. That's how LangSmith and other tracing tools hook in.

Hosted tracing

LangSmith (LangChain's platform) records every trace with no code changes: set LANGSMITH_TRACING=true and LANGSMITH_API_KEY in .env. On Azure, OpenTelemetry traces can go to Application Insights / Azure Monitor, and Azure AI Foundry has tracing built in. The concepts are the same as your tracker.

Traces contain user data Prompts and tool results may include personal information. Decide what to log, mask sensitive fields, and set retention limits.

The Project

A UsageTracker callback handler that records spans with timing, tokens, decisions and errors, then prints a timeline and a cost report for an agent with a knowledge-base tool and a deliberately failing inventory tool.

Goal

  1. Explain traces and spans, and what to measure in LLM apps.
  2. Write a LangChain callback handler for model and tool events.
  3. Compute cost per run from token usage.
  4. Know how to switch to hosted tracing (LangSmith or OpenTelemetry).

Success Criteria

  • The timeline shows each model call (with tokens and its decision) and each tool call
  • The failing inventory tool appears with ❌ and its error
  • The report gives the total cost of the run in USD
  • All 5 checks pass (offline)

Walkthrough

  1. Read the given on_chat_model_start to see how a span is created; mirror it in on_tool_start.
  2. on_llm_end: the message is at response.generations[0][0].message; tokens are in usage_metadata.
  3. The checks use fake models that report token usage, so you can verify the arithmetic exactly.
  4. Optional: enable LangSmith and compare its trace with your timeline.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add latency percentiles (p50, p95) per tool to the report. Done when: the report shows a tool whose p50 is better and whose p95 is worse than another's.
  2. Connect (EXER015). Export the spans as JSON and draw the timeline in Streamlit. Done when: stretch/output/trace.json is written, and the app shows one bar per span from its start to its end.

Common Pitfalls

Streaming without usage

Streamed calls only report tokens if usage is requested (stream_options; LangChain's stream_usage=True). Otherwise your cost report reads zero.

Averages hide spikes

Average cost per question may be fine while 1% of questions loop 30 times. Look at the distribution and the maximum.

Logging secrets

Tool inputs may contain keys or personal data. Mask before you store.

Discussion

Your agent costs $0.02 per question. Is that a lot?

It depends on what the answer is worth. For a support ticket that would cost $5 to handle by hand, it's cheap. For a free consumer feature with 10 million queries a day, it's $200,000 a day. Cost per question needs a business context.

Which step would you optimise first?

The one the trace shows is biggest. Usually it's input tokens from long tool results or history, not the model's output.
