Conversation Memory Strategies

Every long conversation outgrows its budget. Trimming, summarizing and retrieving each forget something different, so measure what each one loses and what it costs.

Overview

Lecture 005 showed that memory is the message list. Lecture 006 trimmed it, and Lecture 028 trimmed it inside a graph. Trimming is the simplest strategy and the most forgetful one: whatever is outside the window is gone. This lecture puts the three standard strategies side by side as functions of the same shape, and compares them on the two things that matter: recall (can the bot still answer questions about the conversation?) and cost (input tokens per question).

Concept

One shape, three strategies

strategy(history, question) -> the messages to send

Written this way, a strategy can be swapped without touching the rest of the application, and all of them can be measured by the same loop.

Trim

Walk the history from the end, keep messages while they fit the budget, and never start on an assistant message whose question was cut. It costs nothing and needs no model. Its failure is total and silent: ask about the first turn and the bot honestly does not know.

Summarize

Replace the old turns with one message written by the model, and keep the last few turns as they are:

[{"role": "system", "content": "Summary of the earlier conversation: Rina Castillo, office manager at Lumen Studio; order #4471 …"},
 *history[-4:]]

The summary prompt decides what survives. "Summarize this conversation" keeps the coffee advice and drops the order number. "Keep every fact about the customer: names, numbers, addresses, dates, preferences, allergies and promises" keeps what a support agent needs. A summary is written once and reused for every later question, until the conversation has grown enough to need a new one.

Retrieve

Treat the conversation as a small knowledge base (Lecture 019). Embed each exchange once, and for every question fetch the most similar ones:

  • Index exchanges, not messages. "It's on the 12th floor" means nothing without the question before it. A question and its answer are one unit.
  • Always add the latest exchange. The user is probably still talking about it, and a search might not rank it.
  • Return them in their original order. A model reads a conversation top to bottom; an answer placed before its question confuses it.

Measure both axes

The probe questions each have keywords a correct answer must contain. Recall is the share of probes answered; cost is the mean size of the context that was sent. One table shows both, and a strategy has to earn its place on it:

strategy              recall  tokens/question
full history            100%             1563     ← the baseline: perfect recall, and the bill grows every turn
trim (400 tok)           33%              386
summary + last 4        100%              275
retrieve 3 + last       100%              234

Tokens per question is not the whole price. The summary cost one model call that read the entire history, and the index cost one embedding call, before the first question was asked. Both pay off quickly in a long conversation and never in a short one.

A summary is lossy in a way you cannot see A trimmed-away fact gives "I don't know". A fact the summary got slightly wrong gives a confident wrong answer. Summaries of summaries drift further each time. For facts that must stay exact (an order number, an allergy), store them as structured data, as the long-term memory of Lecture 028 does.

The Project

Facts are planted early (order number, allergy, delivery floor), in the middle (a wholesale order), late (a promised replacement) and at the very end (an invoice address), with general coffee talk in between. Goal

  1. Implement trimming, summarizing and retrieval over past turns as interchangeable functions.
  2. Say what each strategy loses, and how you would notice.
  3. Measure recall and tokens per question for each strategy on the same conversation.
  4. Choose a strategy for a given kind of conversation, including the setup cost.

Success Criteria

  • The script prints one row per strategy: recall, tokens per question, and what was missed
  • Trimming to 400 tokens forgets the early facts (order number, allergy, floor)
  • Summarizing and retrieving both recall more than trimming, for less than half the tokens of the full history
  • You can say, for each strategy, what kind of fact it loses
  • All 7 checks pass (6 offline, 1 calls your models)

Walkthrough

  1. Read conversation.json and mark where each probe's answer sits. Predict which strategy will miss which probe.
  2. count_tokens and trim_recent first: both are plain Python and checked offline.
  3. summary_and_recent: the summary text is passed in. Writing it is summarize()'s job, once per conversation.
  4. pair_turns, then retrieve_turns: collect positions in a set, sort them, flatten. The offline check uses a toy word-count "embedding", so you can reason about which exchange wins.
  5. evaluate: the loop that produces a row of the table.
  6. Run it, then change one number: trim to 800 tokens, or retrieve 1 exchange. Does the table move the way you expected?

Stretch goals

Common Pitfalls

Summarizing on every turn

That adds a model call that reads the whole history to every question, which costs more than sending the history. Summarize when the thread crosses a threshold, and reuse the summary until it does again.

Retrieving single messages

"Yes, that works." is the most similar message to nothing and the answer to something. Index the question together with its answer.

Retrieved turns in ranking order

The best match first reads like a shuffled conversation. Sort what you retrieved back into its original order.

Comparing strategies on recent questions only

Every strategy answers a question about the last turn. Probes must reach back to the start of the conversation, or the table shows a four-way tie.

Discussion

Which strategy would you ship for a support chat?

Usually a combination: a short running summary for the gist, the last few turns word for word, and exact facts (order number, allergies) in structured memory. Retrieval over turns earns its place when conversations run to hundreds of turns or span several sessions.

The context window is a million tokens. Does any of this still matter?

The table answers it: 1,563 tokens against 234, on every question, for the same recall. At scale that is the difference between two bills. Long contexts are also slower, and details in the middle of them are overlooked more often (Lecture 006).

How is this different from the long-term memory of Lecture 028?

That stored facts about a user, across conversations. This manages the text of one conversation. They combine: the summary and the retrieved turns serve the conversation, the store serves the person.
