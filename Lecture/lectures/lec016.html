Tool Calling by Hand

Models can't check the weather, query a database or do exact math. They can ask your code to do it. Tool calling turns a text generator into something that acts.

Overview

Tool calling (also "function calling") is the foundation of agents. You describe functions to the model; when a question needs one, the model replies with a structured request to call it. Your code runs the function, sends the result back, and the model writes the final answer. We build the whole loop by hand with the raw SDK.

Concept

The loop

sequenceDiagram participant C as Your code participant M as Model C->>M: messages + tools (JSON schemas) M-->>C: assistant message with tool_calls:
get_weather({"city": "Tokyo"}) id=call_1 Note over C: run get_weather("Tokyo") C->>M: messages + assistant(tool_calls) + tool(call_1): {"temp_c": 18} M-->>C: "It's 18°C and clear in Tokyo."
The model never executes anything It only produces JSON that asks for a call. Your code decides whether to run it, which is where all the safety controls live (Lecture 018).

Describing a tool

{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Get the current weather for a city.",      # when to use it
    "parameters": {                                              # JSON Schema of the arguments
      "type": "object",
      "properties": {"city": {"type": "string", "description": "City name, e.g. Tokyo"}},
      "required": ["city"],
      "additionalProperties": False,
    },
  },
}

The model chooses tools based on their name and description. Treat them like prompts: clear, specific, with examples where useful.

The messages involved

# 1. the model's request (keep it in the history!)
{"role": "assistant", "content": None,
 "tool_calls": [{"id": "call_1", "type": "function",
                 "function": {"name": "get_weather", "arguments": "{\"city\": \"Tokyo\"}"}}]}
# 2. your answer, linked by tool_call_id
{"role": "tool", "tool_call_id": "call_1", "content": "{\"city\": \"Tokyo\", \"temp_c\": 18}"}
  • arguments is a JSON string. Parse it with json.loads, and expect it to be invalid sometimes.
  • A model can request several calls at once (parallel tool calls). Answer every one.
  • Return errors as tool results ({"error": "..."}) instead of crashing. The model can read them and recover.

Never eval() model output

calculate uses Python's ast module to walk the expression and allow only numbers and arithmetic operators. eval("__import__('os').system('rm -rf ~')") shows why eval is off-limits.

The Project

An assistant with get_weather(city) (fake data) and calculate(expression), a dispatcher that runs tools safely, and the conversation loop with a round limit.

Q: Is it warmer in Manila or London right now, and by how many degrees?
  -> get_weather({"city": "Manila"}) = {"city": "Manila", "temp_c": 31, ...}
  -> get_weather({"city": "London"}) = {"city": "London", "temp_c": 11, ...}
  -> calculate({"expression": "31 - 11"}) = 20
A: Manila is warmer, by 20°C.

Goal

  1. Describe tools with JSON Schema.
  2. Implement the request → execute → respond loop, including parallel calls.
  3. Return tool errors to the model instead of crashing.
  4. Bound the loop with a maximum number of rounds.

Success Criteria

  • Weather questions call get_weather; math questions call calculate
  • "Is it warmer in Manila or London?" triggers two tool calls in one turn
  • The otter question is answered without any tool
  • All 6 checks pass

Walkthrough

  1. Write both schemas in TOOLS. Run with verbose=True to watch the calls.
  2. run_tool: one try around parse + call, with an except Exception that returns the error as JSON. This is one of the few places a broad except is right: errors must go back to the model.
  3. message.model_dump(exclude_none=True) turns the SDK's message object into a dict you can append to messages.

Common Pitfalls

Missing the assistant message before the tool results

A tool message must follow the assistant message that requested it. Otherwise the API returns 400.

Not answering every tool call

If the model asked for two calls, send two tool messages, one per tool_call_id.

Infinite loops

A confused model can call tools forever. Always cap the rounds.

Vague descriptions

"Does stuff with data" leads to wrong or missing calls. Say what the tool does, when to use it, and what its arguments mean.

Discussion

Why does the model sometimes do math in its head instead of calling calculate?

It decides based on the description and the system prompt. "Use for any math" in the description, or a rule in the system prompt, makes calls more reliable. tool_choice can force a call.

What makes a tool dangerous?

Side effects: sending, buying, deleting, running code. Read-only tools are low-risk; tools that act need confirmation and limits (Lectures 018 and 029).
