Privacy and Data Lifecycle

A helpdesk that remembers people keeps their data in more places than anyone remembers. Deleting a person means finding all of them, including the backup.

Overview

Lecture 028 stored long-term memories, Lecture 035 recorded traces, Lecture 039 indexed past turns, Lecture 042 gave each user a notes file. Each was a good idea on its own. Together they mean that one customer's phone number, typed once into the chat, can sit in five stores and their backups.

This lesson treats personal data as something with a life: what is collected, where it goes, how long it stays, and how it is removed. The rules come from privacy law (the Philippine Data Privacy Act, the GDPR and others), but every step is engineering.

Concept

Where the data goes

flowchart LR U["customer types:
'I'm ana@…, 0917 …'"] --> C["conversations
(SQLite)"] U --> M["memories (L028)"] U --> N["notes file (L042)"] U --> V["index of past turns (L039)"] U --> T["traces (L035)"] C & M --> B["database backups"] U --> P["model provider"]

Every arrow is a decision. The lesson makes five of them explicit.

1. Minimize before the model call

ALLOWED_PROFILE_FIELDS = ("first_name", "loyalty_tier")
minimize({"first_name": "Ana", "loyalty_tier": "Gold", "email": "…", "phone": "…", "address": "…"})
# 'first_name: Ana, loyalty_tier: Gold'

The model needs the first name to greet and the tier to answer reward questions. It does not need the email, the phone number or the address, so they are never sent. Data that is not sent cannot be logged by the provider, leaked by the model, or quoted in a prompt-injection attack (OWASP LLM02: sensitive information disclosure). Check your provider's retention and training settings for what it does with the data you do send.

2. Redact everything derived

The conversation keeps the customer's own words: they may read their history. Everything derived from it (traces, the index of past turns) is redacted, because debugging and retrieval need the meaning of a question, not the phone number.

question  I'm ana.reyes@example.com, 0917 555 0142. Card 4111 1111 1111 1111 was charged twice for NC-1042.
trace     I'm [EMAIL], [PHONE]. Card [CARD] was charged twice for NC-1042.

Patterns catch what they anticipate. A card number is only replaced when it passes the Luhn checksum, so tracking numbers and order ids survive. Names, addresses and free-text descriptions of a person get through any regex; that is why minimization comes first.

3. Retention: data has an end date

Decide how long each kind of data is useful, and delete it after that: traces for 30 days, conversations for 90, for example. purge_expired runs daily and removes old rows, index entries and trace lines. Data you no longer hold cannot leak and does not have to be searched for a deletion request.

4. Deletion everywhere, with a receipt

deletion receipt: {'sqlite:conversations': 2, 'sqlite:memories': 1, 'notes file': 1,
                   'vector index': 1, 'traces': 1}

The receipt lists every store and what was removed from it, so the answer to "did you delete my data?" is a record, not a belief. Deletion must be safe to repeat (a retried request deletes nothing more), and must leave everyone else untouched. find_user_data then searches every store for the user id and the raw values, and must find nothing. Lecture 028 mentioned the GDPR's right to erasure: this is how it is honoured.

5. Backups and tombstones

Backups are meant to bring data back, which is exactly what must not happen to a deleted user. Rewriting every old backup is often impossible. The common answer is a tombstone: a record of the deletion, kept outside the data that gets restored, and applied after every restore.

restoring yesterday's backup ... re-applied deletions: {'ana': 3}
after restore, ana appears in:    []

Backups themselves expire under the retention policy, so a deleted user's data eventually disappears from them too.

Goal

  1. List every store where a user's data ends up, including derived data and backups.
  2. Minimize what is sent to the model and redact what is written to traces and indexes.
  3. Enforce retention periods, and delete one user everywhere with a receipt.
  4. Keep deletions in force across backup restores with tombstones.

Success Criteria

  • Emails, mobile numbers and card numbers (checked with Luhn) are redacted; order numbers and prices are not
  • Only the allowed profile fields reach the prompt
  • Traces and the index of past turns never hold an email, phone or card number
  • Deleting a user removes them from all five stores, returns a receipt, leaves other users alone, and is safe to repeat
  • Restoring a backup taken before the deletion does not bring the user back
  • Data older than the retention period is removed from conversations, the index and the traces
  • All 7 checks pass (offline)

Walkthrough

  1. luhn_ok, then redact: the card pattern matches any long digit run, so pass a function to re.sub that checks Luhn.
  2. minimize: an allowlist, not a blocklist. A new profile field stays out until someone decides it is needed.
  3. delete_user: one block per store, a count for each, then the tombstone.
  4. apply_tombstones and purge_expired: the same deletes, driven by a list of users or by a date.
  5. Run the demo and read find_user_data's output before and after each step.

Stretch goals

Common Pitfalls

Forgetting a derived store

The conversation table is deleted, but the index of past turns, built from it, still holds the text. Keep a list of every store and let deletion and find_user_data use the same list.

Tombstones inside the database

Restoring last week's database also restores last week's tombstone table, without this week's deletions. Keep the record of deletions where a restore cannot reach it.

Treating redaction as complete

Regexes find formats. "My neighbour Maria at the blue house on Maginhawa" passes them all. Minimize first; redact as the second line.

A blocklist for profile fields

"Send everything except email and phone" sends the next field someone adds, a birthday or an ID number, without anyone deciding to.

Logging the deletion request with the data

"Deleted ana.reyes@example.com" in an application log is a new copy of what was just deleted. Log the user id and the receipt.

Discussion

The model provider also received the conversation. What does deletion mean there?

It depends on the provider's terms: whether requests are stored, for how long, and whether they are used for training. Choose a provider and settings where the answer is acceptable before the first request, and say so in your privacy notice. Minimization is the part you control after that.

Why keep the customer's own words in the conversation table at all?

So the customer can scroll back through their history and the assistant can continue the conversation. Both are features the customer wants. The trade-off is a retention period on that table and a deletion that covers it.

What should a trace contain, if not the question?

Enough to debug: the user id, the redacted question, the tools used, token counts and timings. If an engineer needs the raw text to fix a bug, ask the customer, or reproduce it with test data.
