Model Selection and Routing

"Which model?" has measurable answers: quality on your tasks, latency, and cost. Measure them, choose the cheapest model that meets the bar, and re-measure when the model is retired.

Overview

Every exercise so far used one configured chat model. In production that choice is revisited often: a cheaper model appears, the provider retires the one you use, a local model becomes good enough, or one question type is too slow. Each time the question is the same: is the other model good enough for these tasks, and at what cost?

This lesson reuses the course's evaluation habit (Lectures 008, 024, 038) to compare models, then builds two mechanisms around the result: a router that sends each question to the cheapest model likely to answer it, and a fallback for when the provider fails.

General benchmarks rank models on other people's tasks. Your suite ranks them on yours, and it is small enough to run every time something changes.

Choose the cheapest model that meets every bar

bars = {"classify": 0.75, "extract": 1.0, "tool": 1.0}
choose(summaries, bars, max_p95=8.0)     # cheapest qualifying candidate; None if none qualifies

"Best" is the wrong target. If two models both meet the bar, the cheaper one is the better engineering choice. An unknown price is not a zero price: a candidate without one is chosen only when no priced candidate qualifies.

One run is a small sample With four cases in a task, one case is 25 points. The same model can score 0.75 on one run and 1.0 on the next (it happened while this lesson was written). Before switching because of a gap, check that the gap is larger than each model's spread against itself (stretch goal 1).

Route with rules you can read

flowchart LR Q["question"] --> R{"route_question"} R -->|"short, factual"| S["small model"] R -->|"arithmetic, why, complaint,
long, several questions"| L["large model"] S --> E{"needs_escalation?"} E -->|"searched, still 'don't know'
empty, failed"| L E -->|no| A["answer"] L --> A

The router is deliberately a few lines of rules, not a model. When a customer gets a poor answer, you can read why the question went where it went. Learned routers exist (for example RouteLLM), and so do cascades that try models from cheap to expensive (FrugalGPT); both need the same measurements before you can trust them.

Escalation needs a quality signal you can compute. "I don't know" after the small model searched the documents is one: the information was there and the model did not use it. "I don't know" to an off-topic question is not: that is the correct answer. Escalation has a cost too: in the sample run below, a correct refusal was escalated, and the question was paid for twice.

Fall back on provider errors only

PROVIDER_ERRORS = (openai.APIConnectionError, openai.APITimeoutError,
                   openai.RateLimitError, openai.InternalServerError)
primary.with_fallbacks([fallback], exceptions_to_handle=PROVIDER_ERRORS)

A connection error or a 5xx says nothing about your request; another model or provider may answer. A ValueError or a 400 is a bug in your request: it will fail on every model, and a fallback would only hide it while doubling the latency. LangChain's fallbacks take exactly this list.

Models are retired

Hosted models have a lifecycle: providers announce retirement dates, and after that date requests fail (Azure and OpenAI publish them). Keep the dates next to the prices in a registry, warn when one is within 90 days, and run the same suite on the replacement. That suite is usually the reason a team has a model comparison at all.

Goal

  1. Compare models on your own tasks for quality, latency and cost.
  2. Choose the cheapest model that meets every bar, and recognize when a difference is noise.
  3. Route questions with readable rules and escalate on a computable quality signal.
  4. Fall back on provider errors without hiding bugs, and plan for model retirement.

Success Criteria

  • The comparison prints accuracy per task, p50/p95 latency, errors and cost per 1,000 requests for every candidate
  • choose picks the cheapest candidate that meets every bar, prefers a known price, and returns None when none qualifies
  • Easy questions go to the small model; arithmetic, reasons, complaints and long questions to the large one
  • A small model's answer is escalated when it searched and still could not answer, never for a correct off-topic refusal
  • Provider errors fall back to another model; a bug in the request is not hidden
  • Models retiring within 90 days are reported, soonest first
  • All 9 checks pass (one is [live API]: it runs the suite on your model)

Walkthrough

  1. summarize: accuracy per task, then latency, then cost. Return None for an unknown price.
  2. choose: filter by every bar, then sort by a tuple. One min(..., key=...) is enough.
  3. route_question and needs_escalation: the checks list the questions that must go each way.
  4. with_provider_fallback: one line. The check proves a ValueError is not swallowed.
  5. retiring_soon: date arithmetic. Overdue models are the most urgent, so keep them.
  6. Set AICOURSE_COMPARE_MODELS to two candidates and run compare and route.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Run the suite several times per candidate and decide whether their difference is larger than the noise. Done when: the script prints each task's accuracy per run, its spread, and a verdict per task.
  2. Connect (EXER038). Score the capstone's multi-step tool trajectories on every candidate with the EXER038 scorer. Done when: the script prints each trajectory, what is missing, and a total per candidate.

Common Pitfalls

Choosing on a public leaderboard

A model that ranks higher on general benchmarks can still break your schema or pick the wrong tool. Run your suite.

Treating an unknown price as free

A candidate without a price then always wins on cost. Unknown is unknown: rank it last until you know.

A fallback that catches everything

with_fallbacks([...]) without exceptions_to_handle also catches your own bugs. The fallback model fails the same way, the user waits twice as long, and the error in the log is the fallback's, not the original.

Escalating every refusal

Off-topic questions should be refused by the small model. Escalating them pays the large model to say the same thing.

Switching models without re-running the evaluations

A replacement for a retired model is a new model. Run the task suite and the capstone evaluation (Lecture 037) on it before the date, not after.

Discussion

When is a model router not worth it?

When one model already meets every bar at an acceptable cost, or when the traffic is small. A router adds a second model to evaluate, monitor and update. Start with one model; add routing when the cost report says one question type is expensive and a cheaper model passes the suite for it.

A local model passes the suite but its p95 is 12 seconds. What would you do?

Look at where it is acceptable: nightly batch work, internal tools, or the small half of a router with a tight timeout that escalates. The suite gives you the numbers to decide per use, not one verdict for the whole application.

Your provider retires your model in 30 days, and the replacement scores lower on one task. Options?

Improve the prompt or the tool descriptions for that task and re-measure; route that task to another model; or accept a lower bar for it, documented. The worst option is finding out after the retirement date.
