Evaluating RAG

"It looked fine when I tried a few questions" is not evaluation. Build a test set, measure retrieval and generation separately, and use an LLM judge for what code can't check.

Overview

Every change you make (chunk size, prompt, model, retriever) can improve some answers and break others. Without evaluation you can't tell which. This lecture builds a repeatable evaluation that produces a report you can compare over time. It's the single habit that most separates AI engineering from AI demos.

Concept

The golden set

{"question": "How long does a refund take to reach my card?",
 "expected_source": "refund_policy.md",
 "reference_answer": "5 to 7 business days after they receive the returned item."}

Include easy and hard questions, different phrasings, every document, and unanswerable questions (expected_source: null), where the correct behaviour is to refuse.

Measure the two halves separately

MetricQuestion it answersHow
Hit rateDid we retrieve the right document at all?Code
MRRHow high was it ranked? (1/position of the first hit)Code

CorrectnessDoes it match the reference answer in meaning?LLM judge
Refusal rateDoes it say "I don't know" when it should?Code

Separating them tells you where to work: low hit rate means fix retrieval (Lecture 023); good hit rate but low faithfulness means fix the prompt or model.

LLM-as-judge

class Grade(BaseModel):
    reasoning: str = Field(description="Short explanation, written BEFORE choosing the score")
    score: int = Field(ge=1, le=5)

judge_llm.with_structured_output(Grade).invoke(FAITHFULNESS_PROMPT.format(context=..., question=..., answer=...))
  • A clear rubric ("5 = fully supported, 3 = partly, 1 = invents facts") makes scores consistent.
  • Reasoning before score: since fields are generated in order, the model "thinks" first, which improves judgments.
  • Structured output makes scores machine-readable; ge/le enforce the range.
  • Calibrate: check the judge with known good and bad answers (the live check does exactly this).
Judges have biases LLM judges can favour longer answers, their own style, or the first option shown. Spot-check judgments by hand, use a strong model as judge, and never use the judge as the only signal for high-stakes decisions.

Goal

  1. Build and maintain a golden test set, including unanswerable questions.
  2. Compute retrieval metrics (hit rate, MRR) in code.
  3. Implement an LLM judge with a rubric and structured output.
  4. Use a report to decide what to improve next.

Success Criteria

  • The run produces a Markdown report with metrics and a per-question table
  • Hit rate ≥ 0.85, faithfulness ≥ 4.0, refusal rate = 1.0
  • You looked at the lowest-scoring rows and can say why they failed
  • All 6 checks pass

Walkthrough

  1. Implement reciprocal_rank and summarize first. They're plain Python, checked offline.
  2. Write Grade with reasoning first, then score; the check enforces the order.
  3. Run the evaluation, open the report, sort by the worst scores, and read those answers in full.
  4. Change one thing (e.g. k=6 in build_rag_chain), re-run, and compare reports.

Common Pitfalls

Only testing questions you know work

Add the questions real users ask, especially the ones that failed in production.

Changing several things at once

If the score moves, you won't know why. One change per run.

Trusting a single number

Averages hide disasters. One confidently wrong refund policy matters more than a 0.1 drop in average correctness.

Discussion

How big should the golden set be?

Start with 20–50 well-chosen cases and grow it with every bug you find. Each bug becomes a test case.

Can you evaluate without reference answers?

Partly. Faithfulness and refusal behaviour need no reference. Correctness does. Production systems often combine reference-free metrics on live traffic with reference-based tests before release.
