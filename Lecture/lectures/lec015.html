Streamlit Chat App

Put your chatbot in the browser with pure Python. The key idea to grasp is that Streamlit re-runs your whole script on every interaction.

Overview

Streamlit turns a Python script into a web app: no HTML, no JavaScript, no routes. It has built-in chat elements and can stream a generator straight into the page. It's ideal for prototypes, internal tools and demos, which is most of what AI engineers build first.

Concept

The execution model

flowchart TD A[User types a message / clicks a button] --> B[Streamlit re-runs app.py from top to bottom] B --> C[Widgets return their current values] B --> D[Ordinary variables are re-created from scratch] B --> E[st.session_state survives] E --> F[Page is redrawn]

This is the single most important idea. A list created with messages = [] at the top of the script is empty again on every run. Anything that must persist goes in st.session_state, a per-browser-session dictionary.

if "messages" not in st.session_state:       # only on the first run
    st.session_state.messages = []

for m in st.session_state.messages:          # redraw the conversation every run
    with st.chat_message(m["role"]):
        st.markdown(m["content"])

if prompt := st.chat_input("Ask me anything"):   # None unless the user just sent something
    ...

Streaming into the page

with st.chat_message("assistant"):
    answer = st.write_stream(stream_answer(llm, history, system_prompt))   # renders live, returns full text

st.write_stream accepts the same kind of generator you wrote in Lecture 007.

Caching expensive objects

@st.cache_resource creates an object (model client, vector store) once and reuses it across re-runs and sessions. Without it, you'd rebuild the client on every keystroke.

Keep logic out of the UI file

app.py only draws; chat_logic.py converts messages and streams. The logic can then be tested without a browser, and the UI is tested headless with streamlit.testing.v1.AppTest, as the check script shows.

The Project

A chat app with streaming answers, a sidebar for the system prompt and temperature, and a "Clear conversation" button.

uv run streamlit run EXER015/starter/app.py     # opens http://localhost:8501

Goal

  1. Explain Streamlit's rerun model and use session_state.
  2. Build a chat UI with st.chat_message and st.chat_input.
  3. Stream model output with st.write_stream.
  4. Separate UI from logic and test both.

Success Criteria

  • Answers stream into the assistant bubble
  • The conversation stays visible after each message (session state works)
  • Changing the system prompt in the sidebar changes the bot's behaviour
  • "Clear conversation" empties the chat
  • All 5 checks pass

Walkthrough

  1. Complete chat_logic.py and run the checks for its two functions first.
  2. In app.py: initialize state, redraw history, handle the prompt, add the clear button.
  3. Run the app, then edit app.py and save. Streamlit offers to rerun with your change.
  4. Wrap the model call in try/except and show st.error. A raw traceback in the UI is a poor experience.

Common Pitfalls

"My chat history disappears"

You stored it in a normal variable. Use st.session_state.

Messages appear twice

You appended to history and drew it again in the same run. Draw history first, then the new messages, then append.

Session state is per tab and in memory

Refreshing the page or restarting the server loses it. Real apps persist conversations (Lecture 028).

Discussion

When would you outgrow Streamlit?

Many concurrent users, complex layouts, custom branding, fine-grained authentication. Then a web framework (FastAPI backend plus a JavaScript frontend) makes sense. The logic module you wrote stays the same.

Is it safe to show the system prompt in the sidebar?

For a learning tool, yes. In a product, letting users edit the system prompt lets them bypass your rules.
