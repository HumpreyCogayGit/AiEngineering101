Memory and Persistence

Short-term memory remembers this conversation. Long-term memory remembers this person across conversations. LangGraph gives you a component for each.

Overview

In Lecture 005 memory was a Python list that vanished when the program stopped. Real assistants must resume conversations after restarts, keep different users' conversations apart, and remember durable facts ("allergic to dairy") without stuffing every past message into the prompt.

Concept

Short-term memory: checkpointers and threads

Compile a graph with a checkpointer and LangGraph saves the full state after every step, keyed by a thread_id you pass in the config:

graph = builder.compile(checkpointer=InMemorySaver())        # tests
graph = builder.compile(checkpointer=SqliteSaver(conn))      # survives restarts (Postgres in production)

config = {"configurable": {"thread_id": "thread-a", "user_id": "bea"}}
graph.invoke({"messages": [("user", "Hi, I'm Bea")]}, config)
graph.invoke({"messages": [("user", "What's my name?")]}, config)   # previous messages are loaded automatically
graph.get_state(config).values["messages"]                         # inspect the saved conversation

You send only the new message; the checkpointer restores the rest. Checkpoints also make pause/resume (029) and "time travel" debugging possible.

Long-term memory: the Store

flowchart TB subgraph Checkpointer["Checkpointer (per thread)"] T1["thread-a: messages ..."] T2["thread-b: messages ..."] end subgraph Store["Store (per user, across threads)"] M1["('memories', 'bea'): 'Allergic to dairy', 'Name is Bea'"] end T1 -. save facts .-> M1 M1 -. recall into system prompt .-> T2
def chat(state, config, runtime: Runtime):                  # LangGraph injects config and runtime
    facts = [i.value["fact"] for i in runtime.store.search(("memories", user_id))]
    ...
runtime.store.put(("memories", user_id), str(uuid4()), {"fact": "Allergic to dairy"})

Our graph has a save_memories node that asks the model (with structured output) to extract durable facts from each user message and stores the new ones. The chat node injects them into the system prompt.

Keeping the context small: trimming

recent = trim_messages(state["messages"], strategy="last", token_counter=len,
                       max_tokens=20, start_on="human")

The checkpoint keeps everything; the model sees only the recent window plus remembered facts. With token_counter=len, the budget counts messages. Pass a real token counter for token budgets. start_on="human" avoids starting the window on an orphaned AI or tool message.

The Project

A chatbot graph with a SQLite checkpointer, a long-term memory store, fact extraction and history trimming. The demo shows that thread A remembers Bea, thread B (same user, new conversation) knows she avoids dairy, and another user knows nothing about her.

Goal

  1. Persist conversations with checkpointers and thread_ids.
  2. Store and recall per-user facts with a Store namespace.
  3. Access config and runtime.store inside nodes.
  4. Trim history so long threads still fit the context window.

Success Criteria

  • Thread A remembers "Bea"; thread C (another user) does not
  • Thread B (same user, new thread) avoids dairy — long-term memory works
  • Re-running the script restores thread A from SQLite
  • All 6 checks pass (offline)

Walkthrough

  1. Start with recall and compiling with a checkpointer and store. The first two checks should then pass.
  2. Implement chat: facts into the system prompt, trimmed messages to the model.
  3. Implement save_memories: skip facts that are already stored.
  4. Open output/memory.sqlite with any SQLite viewer to see what a checkpoint looks like.

Common Pitfalls

Reusing one thread_id for everyone

Every user then shares one conversation. Thread ids must be unique per conversation, and in a real app tied to an authenticated user.

Remembering everything

"User said hi" isn't a durable fact. Extract selectively, deduplicate, and let users see and delete what you've stored, since privacy laws may require it.

Trimming that breaks tool-call pairs

A window that starts with a ToolMessage whose request was trimmed is invalid. trim_messages options like start_on exist for this.

Discussion

Is extracting memories with an extra LLM call worth it?

It doubles calls per turn. Alternatives: extract only every N turns, in a background job, or let the agent call a save_memory tool when it decides something matters.

What should never go into long-term memory?

Secrets, payment data, and sensitive personal data you have no need for. Memory is data storage, and the usual data-protection rules apply.
