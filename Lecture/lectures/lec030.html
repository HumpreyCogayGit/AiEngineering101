Agentic RAG

Plain RAG always retrieves once and always answers. Agentic RAG checks its own work: is retrieval needed, is what came back relevant, and should it try a better search?

Overview

The RAG chain from Lecture 022 is a straight line, and it fails quietly: it retrieves for "hi there", answers from irrelevant chunks, and never retries a bad search. Graphs let us add decisions and a retry loop around retrieval, combining Module 4 and Module 5.

Concept

flowchart TB S((START)) --> R[route] R -->|small talk| D[direct_answer] --> E((END)) R -->|needs documents| RT[retrieve] RT --> G[grade each chunk] G -->|some relevant| GEN[generate] --> E G -->|none relevant, retries left| RW[rewrite query] --> RT G -->|none relevant, no retries| F[fallback: I don't know] --> E

The decisions

NodeDecisionImplementation
routeDoes this need the documents?Structured output: RouteDecision(needs_retrieval: bool)
gradeIs each chunk relevant to the question?Structured output per chunk: RelevanceGrade(relevant: bool)
after_gradeGenerate, rewrite, or give up?Plain code: count relevant chunks and rewrites
rewriteA better search queryLLM, given the question and the failed query

Note the mix: LLMs make judgments (relevant? needs retrieval?); deterministic code makes control decisions (retry limit). Keeping limits in code guarantees termination.

Custom state, not just messages

class RAGState(TypedDict, total=False):
    question: str              # never changes
    query: str                 # what we search for, may be rewritten
    docs: list[Document]       # retrieved
    relevant: list[Document]   # graded relevant
    answer: str
    rewrites: int
    path: list[str]            # which nodes ran: your debugging trail

Separating question from query matters: the rewrite changes the search, but the answer must still address what the user actually asked.

Cost

Grading is one LLM call per chunk. Use a small, fast model for grading and routing, batch the grading calls, or grade only when retrieval scores are borderline. Measure whether the quality gain justifies the latency.

The Project

An agentic RAG graph over the Nimbus knowledge base. The demo prints each question's path:

Q: Hi there! How are you?                 path: route -> direct_answer
Q: Can I bring my dog to the café?        path: route -> retrieve -> grade -> generate
Q: something about beans going back       path: route -> retrieve -> grade -> generate
Q: What is the GDP of France?             path: route -> retrieve -> grade -> rewrite -> retrieve -> grade -> rewrite -> retrieve -> grade -> fallback
A: I don't know based on the available documents.

The last question is the important one. The model knows France's GDP, and a router that sent "anything not about coffee" straight to direct_answer would happily answer it from memory, with no source. So the router sends every request for information to retrieval and lets the documents decide; only greetings and small talk skip it, and the direct_answer prompt forbids stating facts. A vague question takes the rewrite loop only when the first search finds nothing the grader accepts, so that path depends on your model's judgments.

Goal

  1. Add routing, relevance grading and query rewriting to RAG.
  2. Build a retry loop with a guaranteed limit and an honest fallback.
  3. Design custom graph state for a non-chat workflow.
  4. Weigh quality gains against extra calls and latency.

Success Criteria

  • "Hi there!" skips retrieval
  • "something about beans going back" gets an answer with a citation (directly, or after a rewrite when the first search finds nothing relevant: the path tells you which)
  • "What is the GDP of France?" is sent to retrieval, not answered from the model's own knowledge, and ends in the honest fallback after 2 rewrites
  • The printed path explains every decision
  • All 5 checks pass

Walkthrough

  1. decide and after_grade are routers: they return node names.
  2. grade is a list comprehension calling grader.invoke(...) per document.
  3. Wire the edges from the diagram. The rewrite → retrieve edge creates the loop.
  4. The offline checks script the fake model's judgments, so you can verify every path deterministically.

Common Pitfalls

Unbounded retries

Never let an LLM decide whether to keep looping without a hard cap in code.

Answering the rewritten query

Generate with the original question. The rewrite exists only to search better.

A grader that's too strict

If it marks partially useful chunks as irrelevant, everything ends in fallback. Check grader decisions against a few labelled examples.

Discussion

Agentic RAG or a better retriever?

Fix retrieval first (Lecture 023). It's cheaper per question. Agentic loops help with the remaining hard cases and with deciding when not to retrieve.

Could the agent choose between several knowledge sources?

Yes: the router can pick a source (policies, product catalog, web search), or retrieval becomes a tool the agent calls with its own queries.
