Safe Side Effects

A retried request, a resumed checkpoint, or a crash between "refund issued" and "result saved" can each run the same refund twice.

Overview

Lecture 011 taught retries, Lecture 028 resuming from a checkpoint, and Lecture 029 approval before risky actions. Each of them runs a tool again. For a search that is harmless. For a tool that moves money, sends an email or writes a record, running again means doing it again.

This lesson makes a refund tool safe to repeat. The technique, an idempotency key, is decades older than LLM agents, and payment APIs use it for the same reason. What is new is where the repeats come from, and that the model making the decision is not the place to prevent them.

Concept

Tool calls run at least once

CauseWhat repeats
A client times out and sends the request again (Lecture 011)The whole question, and every tool call in it
A run crashes in the tools node and is resumed (Lecture 028)The whole tools node, with the same tool calls
A tool pauses with interrupt() and is resumed (Lecture 029)The tool function, from its first line
The process dies after the money moved, before the result was storedEverything since the last checkpoint

You cannot make a distributed system run something exactly once. You can make it run at least once and make every run after the first do nothing. That second property is idempotency.

What LangGraph replays

The checkpointer saves state after each step. The model's decision, an AIMessage with tool calls, is saved before the tools node starts. If the process dies inside the tool, invoke(None, config) resumes at the tools node and calls the tool again with the same tool call id in the same thread:

crashed:  power cut
next:     ('tools',)
calls:    [('NC-1042', 3450.0, 'call_X', 't1'),
           ('NC-1042', 3450.0, 'call_X', 't1')]      ← the same call, twice

That makes thread_id + tool_call_id the identity of one decision, and a natural idempotency key. A tool receives both without the model seeing them:

@tool
def refund_order(order_id: str, amount: float,
                 tool_call_id: Annotated[str, InjectedToolCallId], config: RunnableConfig) -> str:
    """Refund money for a Nimbus order. amount is in pesos."""
    key = f"refund:{config['configurable']['thread_id']}:{tool_call_id}"
    return issue_refund(ledger, gateway, key, order_id, amount, actor=...)

  • Record the intent before acting. The "pending" row is written before the gateway is called. After a crash, a pending row is the evidence that the money may have moved.
  • Pass the key downstream. Payment providers accept an idempotency key and return the first result for a repeated one (Stripe's idempotent requests are a well-known example). Then a pending row is safe to retry: the gateway will not pay twice.
  • When the downstream has no keys, stop. An email server or an old internal API cannot tell you whether it already acted. Retrying may pay twice; not retrying may pay nothing. Flag it for a person.
  • Validate in code. The model proposed the amount. The code checks it against what was paid and what was already refunded, counting pending refunds: they may have moved money too.
Code before interrupt() runs twice When a tool pauses with interrupt() and is resumed, the function starts again from its first line, and interrupt() returns the human's answer the second time (LangGraph: interrupts). Never put a side effect before an interrupt(). Stretch goal 1 counts the repeats.

The audit record

Every attempt writes a row: when, the key, who (the agent's thread or the approving person), the order, the amount, and the outcome (started, executed, replayed, rejected, needs_review). The started row is written before the gateway call, so a crash leaves a trace. When a customer says "I was charged twice", the audit log answers in one query.

Goal

  1. Name the four ways an agent's tool call can run more than once.
  2. Derive an idempotency key from the decision, not from the request or the clock.
  3. Record intent before acting, and commit at most once per key.
  4. Recognize when a side effect cannot be made idempotent, and hand it to a person.

Success Criteria

  • The same decision (thread and tool call id) always gives the same idempotency key
  • A refund is refused for an unknown order, a non-positive amount, or more than is left to refund
  • Calling issue_refund twice with one key moves money once and returns the same answer
  • After a crash between "money moved" and "result saved", the resumed agent does not pay again
  • When the gateway has no idempotency keys, an unknown outcome is flagged for a person, never retried
  • The audit log shows every attempt, including the one that crashed
  • All 8 checks pass (offline)

Common Pitfalls

A key made from the arguments

f"{order_id}:{amount}" blocks a legitimate second refund of the same amount (two broken items), and a model that rephrases the amount (3450 vs 3450.0) gets a new key. The key identifies the decision, not its content.

Writing the ledger row after the payment

If the process dies between the two, nothing records that money moved. Write "pending" first.

"Check, then act" without a unique constraint

Two threads both see "no row" and both pay. The database's UNIQUE key (or the gateway's own key) is what makes the check and the insert one step.

Catching the crash inside the tool

A tool that catches every exception and returns "error" to the model invites the model to try again with a new tool call, which is a new key. Let infrastructure failures stop the run; resume it.

Trusting the prompt to prevent double refunds

"Never refund the same order twice" does nothing when the repeat comes from a retry or a replay: the model is not even called again.

Discussion

How long must the ledger remember a key?

At least as long as any retry or resume can arrive. Payment providers keep keys for about a day; a checkpoint can be resumed much later. Keep the ledger at least as long as the checkpoints, and the audit log as long as finance requires.

Which of the capstone's tools need this treatment?

notes_add_note creates a new note on every call, so a replay makes a duplicate. Search and the calculator change nothing and are safe to repeat.

Why is "needs review" a good outcome and not a failure?

Because the alternative is guessing with someone's money. A small queue of cases a person checks is cheaper than either double payments or missing ones, and the reconciliation in stretch goal 2 finds them.
