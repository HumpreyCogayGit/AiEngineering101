Structured Output in LangChain

Turn messy documents into validated Python objects with one method call, then check that the values make business sense, which no schema can guarantee.

Overview

Lecture 009 used the SDK's parse(). LangChain offers the same capability for any chat model through with_structured_output(), and the result is a runnable you can put in chains. We extract invoices in three very different formats and add a second layer of validation: do the numbers add up?

Concept

with_structured_output

class LineItem(BaseModel):
    description: str = Field(description="What was bought")
    quantity: float = Field(description="Number of units (hours count as units)")
    unit_price: float = Field(description="Price of one unit, without currency symbol")

class Invoice(BaseModel):
    invoice_number: str = Field(description="The invoice number or id, exactly as written")
    date: str = Field(description="Issue date in ISO format YYYY-MM-DD")
    line_items: list[LineItem] = Field(description="Every billed item, including fees")
    total: float = Field(description="The total amount due as stated on the invoice")
    ...

parser = llm.with_structured_output(Invoice)
invoice = parser.invoke([("system", "Extract the invoice data."), ("human", text)])   # -> Invoice

Nested models (list[LineItem]) work naturally. Field descriptions guide the model on ambiguous details, for example that "4 hours at $120/hour" is a quantity of 4. Not every provider shows the descriptions to the model (Lecture 009): Ollama only enforces the shape. So repeat the rules that matter, such as the date format, in the system instruction.

Two layers of validation

flowchart LR T[Invoice text] --> S[Schema validation
types and required fields] --> B[Business validation
items add up to total?] --> OK[Accept] S -- invalid --> R1[Retry / repair] B -- mismatch --> R2[Flag for review]

The schema guarantees shape. Business rules catch wrong values: a misread price, a missed fee, an invented line item. Rules like "sum of items equals total" are cheap, deterministic checks on non-deterministic output. Use them whenever your domain has them.

Failing gracefully: include_raw=True

result = llm.with_structured_output(Invoice, include_raw=True).invoke(messages)
# {"raw": AIMessage, "parsed": Invoice | None, "parsing_error": Exception | None}

Instead of raising, you get the raw message and the error, which you can log, retry or route to a person.

The Project

An invoice parser for EXER014/invoices/: a formal table, a casual email ("4 hours at $120/hour"), and a hosting statement. Every invoice should come out with an ISO date and line items that add up to the stated total.

Goal

  1. Design nested Pydantic schemas with helpful field descriptions.
  2. Extract data with with_structured_output.
  3. Add business-rule validation on top of schema validation.
  4. Handle parsing failures without crashing.

Success Criteria

  • All three invoices parse into Invoice objects with correct totals
  • Dates in three different formats all come out as YYYY-MM-DD
  • Every invoice prints [OK] — the line items add up
  • All 5 checks pass

Walkthrough

  1. Write the Invoice fields with descriptions; the check requires them.
  2. validate_totals: compare with a tolerance (abs(a - b) <= 0.01). Never compare floats with ==.
  3. If invoice 002 fails, check how the hourly fee was extracted, and improve the quantity description.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Make the parser return a list of problems (parse errors and broken business rules) instead of raising. Done when: the three invoices print ACCEPT, and an invoice with a wrong total prints REVIEW with the reason.
  2. Connect (EXER012). Parse the invoices concurrently with batch. Done when: the results come back in input order, and the script prints the speed-up over one at a time.

Reference code, for after you have tried: EXER014/stretch/

Common Pitfalls

Floats for money

Floats can't represent 0.1 exactly. For real accounting use Decimal or integer cents. Floats with a tolerance are fine for this exercise.

The model "fixes" the total

Models sometimes compute the total instead of copying it, which hides real discrepancies. The description says "as stated on the invoice" for this reason.

Over-large schemas

Fifty fields in one schema make extraction less accurate. Extract what you need, or split into several focused calls.

Discussion

An invoice fails the total check. Is the model wrong, or the invoice?

Either is possible, and that's the point. Route mismatches to a person rather than auto-correcting. Many real invoices contain errors, and finding them is valuable.

How would you know your parser is 98% accurate?

A labelled set of invoices with expected values, scored field by field. The same evaluation discipline as Lecture 008, applied to extraction.
