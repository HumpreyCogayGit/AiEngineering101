Setup and First Check

Before talking to any model you need a reproducible environment and a safe place for secrets. This lecture sets up both: a virtual environment pinned by uv.lock, and a git-ignored .env that is validated before any request goes out.

Overview

An AI application is ordinary software plus a remote model. Most early frustration comes not from the model but from the environment: the wrong Python, a missing package, a key pasted in the wrong place. We fix that once, at the root of the repository, so all 40 exercises share one configuration.

You will meet four ideas: virtual environments, dependency locking, configuration through environment variables, and inference providers.

Concept

Virtual environments and uv

A virtual environment is a directory with its own Python interpreter and its own installed packages, isolated from the system Python and from other projects, so two projects can pin different versions. uv creates it (.venv/), installs the exact versions pinned in uv.lock, and runs commands inside it with uv run. Two people who run uv sync on the same lockfile get the same packages.

pyproject.toml   what we need     ("langchain", "streamlit", ...)
uv.lock          exactly what we got  (langchain==1.5.0, ...)  ← reproducibility
.python-version  which Python     (3.12)
.venv/           the installed environment (never commit it)

Configuration lives outside the code

Endpoints, model names and keys change between machines and environments (dev, test, prod). The twelve-factor rule is: store config in the environment. Locally we use a .env file that is loaded into environment variables and never committed.

aicourse/settings.py uses pydantic-settings to read and validate the values. It fails early with a readable message (for example "AZURE_OPENAI_API_KEY: is missing") instead of a confusing 401 deep inside a request.

Inference providers

An inference provider is whatever runs the model and answers your API calls. The course supports two, selected with AICOURSE_PROVIDER in .env:

ProviderWhere the model runsBase URLWhat you send as model
azure: Azure FoundryIn the cloud, pay per tokenhttps://<resource>.openai.azure.com/openai/v1/Your deployment name
ollama: OllamaOn your machine, freehttp://localhost:11434/v1/The name ollama list shows, e.g. gemma4:e4b

Both speak the same OpenAI-compatible v1 API, so the standard openai SDK and LangChain's ChatOpenAI work with either: only the base_url, key and model name differ. aicourse/settings.py reads the selected provider's block and exposes provider-neutral settings (base_url, api_key, chat_model, embedding_model). No exercise names a provider, so the code you write runs on both.

chat_model · embedding_model"] N --> C["your code"]

Azure Foundry: resource, deployment, endpoint

TermMeaning
ResourceThe Foundry (Azure OpenAI) resource you create in your Azure subscription. It holds your deployments and has an endpoint URL and keys.
ModelA model family/version, e.g. gpt-4.1-mini.
DeploymentA named instance of a model in your resource, with its own quota. Your code addresses the deployment name.

Ollama: server, model, tag

TermMeaning
ServerThe Ollama program on your machine. It listens on http://localhost:11434 and needs no key.
ModelWeights you downloaded with ollama pull. The first request loads them into memory.
TagThe part after the colon (gemma4:e4b): a size or variant of the model. Your code addresses the full name with its tag.

Secrets hygiene

  • Never hard-code keys in source files, notebooks or screenshots.
  • Never print a key. Print a masked version: abcd****wxyz.
  • If a key leaks, rotate it (regenerate in the portal). Deleting the commit is not enough.
  • In production, prefer keyless authentication (Microsoft Entra ID / managed identity) and a key vault.

Goal

  1. Install the course environment with uv sync and run code with uv run.
  2. Set up an inference provider: a chat model deployment in Azure Foundry, or a chat model pulled into Ollama.
  3. Configure .env and understand how settings flow into every exercise.
  4. Handle secrets safely: mask, ignore, rotate.

Success Criteria

  • uv sync completes and uv run python --version shows 3.12.x
  • .env exists at the repository root and is ignored by git
  • check_setup.py prints your provider, endpoint and model names, with the key masked
  • All checks in check.py pass

Walkthrough

  1. Follow the setup guide to install uv, run uv sync, deploy a model and fill in .env.
  2. Open EXER001/starter/check_setup.py. Each TODO function raises NotImplementedError until you replace it.
  3. python_version_ok(): sys.version_info is a tuple like (3, 12, 14, 'final', 0), and tuples compare element by element.
  4. masked_key(): string slicing. key[:4] gives the first four characters, key[-4:] the last four.
  5. load_config(): one line. aicourse/settings.py does the reading, validation and provider selection, so read it once.
  6. Run the script, then the checks. Run check.py --solution to see the reference pass.
How the checks work check.py imports your file from starter/ and calls your functions. A TODO line means the function still raises NotImplementedError. Add -v to see full tracebacks.

Common Pitfalls

Running from inside the exercise folder

Commands assume the repository root (uv run python EXER001/check.py). uv finds the project from there, and settings.py finds .env next to pyproject.toml.

Azure: using the model name instead of the deployment name

If you named your deployment my-chat, then AZURE_OPENAI_CHAT_DEPLOYMENT=my-chat, even though the model is gpt-4.1-mini.

Ollama: leaving the tag off the model name

gemma4 means gemma4:latest, which may be a different model from gemma4:e4b, or one you never pulled. Copy the name from ollama list.

Quotes or spaces around values in .env

KEY = "abc" can work with some loaders and not others. Write KEY=abc.

Committing .env "just once"

Git history keeps it forever, and bots scan public repositories for keys within minutes. Rotate the key.

Discussion

Why validate configuration at startup instead of when it's first used?

Fail fast. A missing key found at startup gives a clear message. Found mid-request, it surfaces as a confusing HTTP error, possibly after the program has already done half its work.

Why does Azure separate "model" and "deployment"?

You may run several deployments of the same model with different quotas, versions or content-filter settings (e.g. one for production, one for experiments) and switch between them without changing code.

Why can one codebase run on a cloud provider and on a local one?

Both implement the same HTTP API, and the code depends on that API, not on the company behind it. Everything provider-specific is confined to one settings file, so switching is a configuration change, not a code change.

What would change in production?

Keys would live in Azure Key Vault or be replaced by managed identity, and configuration would come from the hosting platform's environment variables rather than a file.
