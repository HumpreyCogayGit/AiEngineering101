Capstone: Nimbus Helpdesk

Combine everything into one assistant that customers and staff could use, then measure it against an evaluation set and write a review of what still fails.

Overview

The capstone is a complete, small product: a helpdesk assistant for Nimbus Coffee Co. with grounded answers from the knowledge base, exact arithmetic, note-taking through an MCP server, conversation memory, guardrails, two interfaces (CLI and web), and an evaluation that gates quality. Most pieces come from earlier lectures; the work is integrating them well.

The Reply contract

@dataclass
class Reply:
    answer: str
    tools_used: list[str]   # e.g. ["search_knowledge_base", "calculator"]
    blocked: bool           # a guardrail stopped it
    reasons: list[str]      # which guardrail and why
    tokens: int             # for cost tracking

A structured return value lets every interface, test and evaluation see what happened, not just the text.

Evaluation as the definition of done

{"question": "What does 3 bags of Barako Bold plus one Hand Grinder Pro cost in total?",
 "expect_keywords": ["4620"], "expect_tools": ["search_knowledge_base", "calculator"]}

Each case says what a correct answer contains and which tools must have been used (so a lucky guess doesn't pass). Blocking cases check the guardrails. The run writes output/capstone_eval.md.

Goal

  1. Integrate RAG, tools, MCP, memory and guardrails into one agent.
  2. Serve one core through two interfaces.
  3. Define "done" with an evaluation set, and reach the bar.
  4. Review your own system critically: cost, failures, remaining risks.

Success Criteria

  • All 11 checks pass, including the live evaluation (≥ 80% of eval_set.json)
  • The CLI and the web UI give the same answers
  • Conversations remember earlier turns within a thread
  • Prompt-injection attempts are blocked before reaching the model
  • You wrote a short review (below) of your own assistant

Walkthrough

  1. Tools first. Implement and check tools.py. Reuse aicourse.rag and your EXER034 connection code.
  2. The core. Assistant.ask is the heart: guard, invoke with a thread id, collect new messages, guard again. The offline checks run it with a fake model.
  3. Interfaces. The CLI ask command, then the Streamlit answer block. Both are thin.
  4. Evaluate. Write score_case, run cli.py eval, and open the report.
  5. Iterate. For each failing case: was it retrieval, tool use, or wording? Fix the system prompt, a tool description, or retrieval, then re-run.
  6. Review. Score yourself with the rubric in the README and write REVIEW.md.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add one new tool and two evaluation cases that need it. Done when: the two new cases pass only when the tool is used, and the original eight still pass.
  2. Connect (EXER035). Attach the EXER035 tracker to the evaluation run and report its cost. Done when: the script prints model calls, tokens and cost for the run and per question.

Common Pitfalls

Counting tools from the whole thread

The checkpointer returns all messages in the thread. Count only messages after the last HumanMessage, or turn 2 reports turn 1's tools.

Async in Streamlit

MCP tools are async. Call asyncio.run(assistant.ask(...)) from the Streamlit script; don't create event loops by hand.

Overfitting to the eval set

Adding "if question mentions Barako say 4620" to the prompt passes the test and teaches nothing. Add your own cases (the rubric rewards it).

Discussion

What's missing before real customers could use this?

Authentication and per-user data, persistent storage (SQLite or Postgres checkpointer), rate limiting, monitoring and alerting, a feedback button feeding the eval set, a human escalation path, deployment (e.g. Azure Container Apps), and a privacy review of what's logged.

Which earlier lecture would improve the eval score the most?

Look at your failures: retrieval misses point to 023 (hybrid search); wrong arithmetic points to tool descriptions (016); answers from outside knowledge point to grounding (022) or agentic checks (030).

Where do you go from here?

Deployment and operations (Lecture 041 starts there), fine-tuning and distillation for cost, voice and real-time interfaces, and deeper evaluation (online A/B tests, user feedback loops).
