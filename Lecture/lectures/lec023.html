Better Retrieval

If the right chunk isn't retrieved, no prompt can save the answer. Learn the standard techniques for improving retrieval, and measure which ones actually help.

Overview

When a RAG answer is wrong, check retrieval first. Vector search has predictable weaknesses: exact terms (product codes, names, numbers), vague or oddly worded questions, and near-duplicate results crowding out variety. Each technique here targets one weakness, and each has a cost. The deciding tool is a metric: hit rate.

Concept

1. Hybrid search: keywords + vectors

BM25 (Okapi BM25, from Robertson and colleagues' probabilistic relevance framework) is the classic keyword ranking: it rewards query words that appear in a chunk, weights rare words more (inverse document frequency), gives diminishing returns for repeating a word, and corrects for chunk length. It's strong where embeddings are weak: "Liberica", "BL-2026-0412", "Maginhawa". Combining both approaches is called hybrid search.

2. Reciprocal Rank Fusion (RRF)

BM25 scores and cosine distances aren't on the same scale, so you can't simply add them. RRF uses only ranks:

(Cormack, Clarke and Büttcher, SIGIR 2009, where k = 60 comes from.)

score(doc) = Σ over rankings of  1 / (k + rank)        k = 60

doc A: rank 1 in vector, rank 3 in BM25  → 1/61 + 1/63 = 0.0323
doc B: rank 2 in vector, rank 1 in BM25  → 1/62 + 1/61 = 0.0325   ← wins: high in both
flowchart LR Q[Question] --> V[Vector search top 10] --> F[RRF fusion] Q --> B[BM25 top 10] --> F F --> K[Top k]

3. MMR: diversity

Maximal Marginal Relevance (Carbonell and Goldstein, 1998) picks each next result to be relevant to the query and different from those already picked, with a weight that sets the balance between the two. Use it when the top results are near-duplicates.

4. Multi-query rewriting

Ask the model for several rephrasings ("money back" → "refund policy", "return window"), search with each, and fuse the results. It helps with vague questions. Cost: one extra LLM call and several searches per question.

5. Reranking

Retrieve a wide set of candidates cheaply (e.g. 10), then reorder them with a stronger relevance judge, such as an LLM or a cross-encoder reranker model, and keep the top 4. It's precise and slower, so use it when quality matters more than latency.

Measure: hit rate @ k

hit rate = share of test questions whose expected source appears in the top k results

data/eval_questions.json holds 20 questions. 19 name the source file that answers them; the 20th is out of scope on purpose (Lecture 024 uses it), so hit rate is computed over 19. Every technique gets a number, and you keep only what improves it.

Pick k to match the question you are asking. With k = 4 you ask "is the right document somewhere in what the model will read?". On a small knowledge base nearly every strategy passes that, so the table tells you nothing. With k = 1 you ask "is the right document ranked first?", which is where the strategies separate:

Hit rate on 19 questions:

  strategy          @1    @4
  vector           84%  100%
  mmr              84%   95%
  bm25             79%  100%
  hybrid           89%  100%
  multi-query     100%  100%
  hybrid+rerank   100%  100%

Read it row by row. Hybrid beats either of its parts at @1, which is the argument for fusion. MMR trades a little relevance for diversity and loses a hit at @4. Multi-query and reranking reach 100% at @1, and each pays for it with a model call per question. Whether that is worth it depends on how much the answer improves, which is the subject of Lecture 024. A metric that every candidate maxes out is not measuring anything: tighten it until it discriminates.

Worked example: one question, four rankings

Question: "Which coffee is best for a strong espresso?" The answer is in the product catalog (products.md, chunk 13: "Barako Bold … our best seller for espresso"). Chunks are written as file#chunk_id.

vector  1. brewing_guide.md#1   2. products.md#13   3. products.md#12      4. brewing_guide.md#0
bm25    1. products.md#13       2. brewing_guide.md#1   3. brewing_guide.md#0   4. shipping.md#18

Vector search puts the wrong chunk first. brewing_guide.md#1 is the chunk with the "## Espresso" section: it is about espresso, so it is closest in meaning, but it explains how to brew, not which bean to buy.

BM25 gets it right. The query is tokenized to which, coffee, is, best, for, a, strong, espresso. The catalog chunk contains "strong", "espresso" and "best" in one sentence about one bean and scores 6.20; the brewing chunk scores 4.88.

RRF fuses the two rankings using positions only:

brewing_guide.md#1   1/(60+1) + 1/(60+2) = 0.0164 + 0.0161 = 0.0325
products.md#13       1/(60+2) + 1/(60+1) = 0.0161 + 0.0164 = 0.0325    ← a tie
brewing_guide.md#0   1/(60+4) + 1/(60+3)                    = 0.0315

First in one list and second in the other, both ways round: the two chunks get exactly the same score. The fused list keeps the wrong chunk first, because a tie is broken by which chunk was seen first. Fusion did not fix this question; it only confirmed that these two chunks are the candidates. This is one of the questions behind hybrid's 89% at @1.

Multi-query asked the model for three rephrasings:

best coffee beans for strong espresso
dark roast high-caffeine beans for bold espresso shots
robusta vs arabica coffee beans for intense full-bodied espresso

Each one adds the word "beans" or names a roast. The question never said "beans"; the catalog is full of them. More rankings that favour the catalog break the tie.

Reranking gave the ten fused candidates to the model and asked for a relevance score each:

rerank  1. products.md#13   2. brewing_guide.md#1   3. brewing_guide.md#0   4. products.md#12

The model can read that one chunk recommends a bean and the other describes a method, which no word count or vector distance can. That judgement cost one model call for one question.

At @4 every strategy passes this question: the catalog chunk is in everyone's top four. At @1 only BM25, multi-query and reranking do. Which of those you need depends on whether the model, reading four chunks, finds the right one anyway. Lecture 024 measures exactly that.

The Project

Implement BM25 search, RRF, multi-query and the hit-rate metric, then print a comparison table of six strategies: vector, MMR, BM25, hybrid, multi-query and hybrid + rerank.

Goal

  1. Explain the typical failure modes of vector search.
  2. Implement BM25 keyword search and reciprocal rank fusion.
  3. Use multi-query rewriting, MMR and LLM reranking.
  4. Compare strategies with hit rate and reason about their cost.

Success Criteria

  • A hit-rate table for six retrieval strategies is printed, at @1 and @4
  • BM25 finds exact rare words such as "Liberica"
  • Hybrid retrieval scores at least as well as plain vector search, and at least 80%
  • You can explain the cost (latency, tokens) of multi-query and reranking
  • All 7 checks pass

Walkthrough

  1. BM25Okapi takes a list of tokenized chunks; get_scores(query_tokens) returns one score per chunk.
  2. RRF: accumulate scores in a dict keyed by chunk_id(doc), then sort.
  3. Work out the RRF check by hand before running it. It's good practice for reasoning about rankings.
  4. Look at the questions each strategy misses. Patterns tell you what to fix next.

Common Pitfalls

Adding raw scores from different systems

A BM25 score of 12 and a cosine distance of 0.3 aren't comparable. Fuse ranks (RRF) or normalize carefully.

Tuning on a tiny test set

19 questions is a start. One question changes hit rate by about 5 points, so don't over-read small differences.

Stacking every technique

Multi-query plus reranking adds two model calls to every question, often for a small gain. Add complexity only when the metric justifies it.

Discussion

Hit rate is high, but answers are still bad. Why?

Retrieval found the right document, but maybe not the right chunk, or the generation step misused it. Lecture 024 evaluates generation separately.
