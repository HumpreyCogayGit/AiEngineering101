Evaluating Agents

A right answer reached the wrong way is a wrong answer waiting to happen. Score what the agent did (its tool calls) as well as what it said.

Overview

Lecture 024 evaluated a RAG chain: one retrieval, one answer, both scored. An agent is harder to evaluate because it chooses its own steps. Ask an order assistant for a total and it may look the prices up and use the calculator, or it may recall a price from an earlier conversation and add in its head. Both can print "₱2,210". Only one of them will still be right after the price list changes.

The list of tool calls an agent made during one run is its trajectory. This lecture builds a scorer for trajectories, in plain code, and uses it to evaluate an agent on a small set of cases.

Concept

Final answer or trajectory?

The capstone already took one step in this direction: its cases list expect_tools. That checks which tools were used at all. A trajectory score also looks at order and arguments.

Strict enough, not stricter

The art is in what you do not require. A scorer that demands an exact copy of your reference run fails good agents all day, and people stop trusting it.

TolerateHow
Two lookups in either orderOrder is a subsequence test on tool names: lookup, lookup, calculator matches whichever product came first
Calls in betweenA subsequence allows extras between the expected calls. Whether an extra call is a failure is the tools check's decision, not the order check's
Spelling of arguments" barako bold " equals "Barako Bold": compare text without case and outer spaces
Different arithmetic, same result{"evaluates_to": 2210} accepts 3*390 + 2*520 and 1170 + 1040
def in_order(actual: list[str], expected: list[str]) -> bool:
    position = 0                                  # the next expected name we are waiting for
    for name in actual:
        if position < len(expected) and name == expected[position]:
            position += 1
    return position == len(expected)

in_order(["lookup", "hours", "calculator"], ["lookup", "calculator"])   # True
in_order(["calculator", "lookup"],          ["lookup", "calculator"])   # False

Where the trajectory comes from

You already have it. Every AIMessage in the result carries tool_calls, each with a name and parsed args (Lecture 017). Walking the messages in order gives the trajectory, with no extra instrumentation. A message can hold several calls: keep them all.

A report that helps

"FAIL" tells you nothing. Each failed case should say what was wrong, in words: missing call: calculator, extra call: store_hours, wrong arguments for lookup_product: expected {'name': 'Barako Bold'}. That line is what you paste into the bug report.

No judge needed Comparing tool calls is exact work, so it is done in code: free, instant and repeatable. Keep the LLM judge of Lecture 024 for what code cannot read, such as whether the final wording is faithful.

Goal

  1. Explain why an agent's final answer is not enough to evaluate it.
  2. Extract a trajectory from a run's messages.
  3. Score tools, order and arguments in code, tolerating harmless variation.
  4. Report failures in words someone can act on.

Success Criteria

  • The script prints PASS or FAIL per case with the trajectory, and writes output/agent_eval.md
  • An agent that gives the right answer without calling its tools fails
  • 3*390 + 2*520 and 1170 + 1040 both count as the right calculator argument
  • Every failed case says what was wrong: a missing call, an extra call, a wrong order or wrong arguments
  • All 8 checks pass (7 offline, 1 calls your model)

Walkthrough

  1. Read cases.json and agent_under_test.py. For each case, say out loud which calls you expect before you look.
  2. extract_trajectory: a nested loop over messages and their tool_calls. Test it on the scripted messages in check.py.
  3. missing_and_extra: copy actual, remove one entry per expected name. Counts matter: one lookup when two were expected leaves one missing.
  4. in_order: the six lines above. Check the empty cases by hand: an empty expected is always in order.
  5. score_trajectory: combine the three, and write one problem line per thing that is wrong.
  6. Break the agent on purpose: remove "calculator for every calculation" from SYSTEM and run the script again. Which check notices?

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add an efficiency score: flag redundant calls (same tool, same arguments) and runs that used more calls than expected. Done when: three hand-written runs that all reach the right answer get efficiency 1.0, 0.5 and 0.5, with each redundant call named.
  2. Connect (EXER037). Score the trajectories of the capstone assistant with your scorer. Done when: for three capstone questions the script prints the trajectory, what is missing or extra, and whether it is in order.

Common Pitfalls

Demanding an exact match

Requiring the same calls in the same order with the same strings fails an agent that looked the two products up the other way round. The team learns to ignore the red rows, and then misses the real one.

Scoring only the answer

An agent that guesses ₱390 passes today. The scripted "guesser" in check.py shows it: right text, no lookup, and it must fail.

Forgetting the "no tool" case

An agent that calls a tool for "thanks, bye" wastes a round trip on every greeting. Include cases whose expected trajectory is empty.

One number for everything

A pass rate of 67% does not say whether to fix the prompt, a tool description or the arguments. Report tools, order and arguments separately.

Discussion

Is an extra tool call always a failure?

No. A second search in a RAG assistant is cheap and often right; a second send_email is a disaster. Decide per tool: for read-only tools you may tolerate extras and track them as a cost, for tools that act you should not.

What if there are several correct trajectories?

Then say so in the case: list the alternatives, or loosen the check that is too strict (drop order, accept any argument). When "correct" becomes hard to write down, a judge model can compare the trajectory with a description of acceptable behaviour, at the cost of exactness.

Where do the cases come from?

From the same place as the golden set of Lecture 024: real questions, and every failure you find. A production trace (Lecture 035) of a bad run is a test case with the expected calls still to be filled in.
