Tools in LangChain

A decorator writes the JSON schema for you, bind_tools attaches it, and create_agent runs the loop you wrote by hand in Lecture 016.

Overview

Writing JSON schemas by hand is tedious and error-prone. LangChain generates them from ordinary Python functions, standardizes tool calls across providers, and ships a ready-made agent loop. You'll use all three layers and see how they map to Lecture 016.

Concept

@tool: schema from signature and docstring

@tool
def convert_currency(amount: float, from_currency: str, to_currency: str) -> str:
    """Convert an amount between currencies. Currencies are ISO codes like USD, EUR, PHP."""
    ...

convert_currency.name         # 'convert_currency'
convert_currency.description  # the docstring
convert_currency.args         # {'amount': {'type': 'number'}, 'from_currency': {'type': 'string'}, ...}

Type hints become JSON types; the docstring becomes the description. Your Python code is now your tool specification.

Parallel tool calls

A model can ask for several tools in a single reply. "How much is 2500 PHP in EUR, and what's the weather in Tokyo?" needs two independent facts, so the model requests both at once instead of taking two round trips:

ai_msg.tool_calls
# [{'name': 'convert_currency', 'args': {'amount': 2500, 'from_currency': 'PHP', 'to_currency': 'EUR'}, 'id': 'call_a'},
#  {'name': 'get_weather',      'args': {'city': 'Tokyo'},                                              'id': 'call_b'}]

Three rules follow from this:

  • Loop over tool_calls, never read only the first one. Code that handles tool_calls[0] works in every demo and breaks on the first compound question.
  • Answer every call before calling the model again. Each call needs its own ToolMessage whose tool_call_id matches. A missing answer is a 400 error from the API.
  • The calls are independent, so you may run them concurrently. Your loop runs them one after another, which is fine for fast tools. create_agent runs them in parallel for you.

When the calls must not be issued together (the second needs the result of the first, or the tool has side effects you want one at a time), turn the feature off: llm.bind_tools(TOOLS, parallel_tool_calls=False). The model then requests one tool per turn.

Reading the answer: .text, not .content

Once tools are involved, AIMessage.content is not reliably a string. Depending on the model and the API LangChain uses for it, it can be a list of content blocks. ai_msg.text always gives you the text, so use it whenever you want the answer as a string (Lecture 012 explains why).

Error handling differs by layer

In your own loop you decide what happens when a tool raises. You'll catch the exception and return an error ToolMessage. Prebuilt agents have their own policies: create_agent re-raises tool exceptions by default, while LangGraph's ToolNode(handle_tool_errors=True) returns them to the model (Lecture 027). Know which one you're using.

Goal

  1. Define tools with @tool, type hints and docstrings.
  2. Use bind_tools, AIMessage.tool_calls and ToolMessage.
  3. Handle parallel tool calls: several requests in one model reply.
  4. Use the prebuilt create_agent, and know what it does for you.

Success Criteria

  • The script prints the auto-generated schema of convert_currency
  • One question triggers both convert_currency and get_weather, and the trace shows one ToolMessage per tool call
  • Your loop and create_agent give equivalent answers
  • All 7 checks pass

Walkthrough

  1. Decorate convert_currency, add the type hints and a docstring, and implement it. Raise ValueError for unknown currencies.
  2. Add word_count and put all three in TOOLS.
  3. run_tool_loop is the Lecture 016 loop with LangChain types. Compare the two side by side. Make the inner loop handle every entry of ai_msg.tool_calls.
  4. build_agent is a single line.

Common Pitfalls

Missing type hints or docstring

Without hints, argument types become vague; without a docstring, @tool raises an error. Both are the model's only guide.

Handling only the first tool call

ai_msg.tool_calls[0] silently drops the others. The next model call then fails with "tool_call_id ... did not have response messages". Loop over all of them.

Returning huge objects from tools

Everything a tool returns goes into the context window. Return what the model needs, not whole database rows.

An uncaught tool exception ends the agent run

Validate inputs and return friendly errors from tools, or use error handling in the tool node.

Discussion

When would you write your own loop instead of using create_agent?

When you need custom control: approval before certain tools, special routing, custom state. LangGraph (Module 5) is the structured way to do that.

How many tools can one agent handle?

Tool selection gets less accurate as the list grows, and every schema costs tokens on every call. Keep toolsets focused, or split them across agents (Lecture 031).
