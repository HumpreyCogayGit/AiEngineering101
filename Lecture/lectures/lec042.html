Identity and Tenant Boundaries

The EXER041 service lets the caller choose the thread_id. Anyone who learns one can read and continue another person's conversation.

Overview

Module 9 takes the deployed helpdesk from Lecture 041 and fixes what stands between it and real users. This first lesson is about who is calling. The service answers anyone who can reach it, stores every conversation under an id the client picks, writes every caller's notes to one shared file, and lets every caller search the employee handbook. None of that is visible in a demo with one user.

The fix is not a feature of the model or the agent. It is the same work as in any multi-user web service: authenticate the request, derive the user from the credential, put the user into every key, and check permissions where data is read. The AI part adds one twist: retrieval is a read, and what is retrieved goes into a prompt.

Concept

Authentication and authorization are two questions

AuthenticationAuthorization
QuestionWho is calling?May this caller do this, to this object?
AnsweredOnce per request, from the credentialAt every read and write of user data
Failure code401 with WWW-Authenticate404 (or 403)

The most common API vulnerability is a missing authorization check on an object id the client sends: OWASP API1:2023, Broken Object Level Authorization. POST /ask {"thread_id": "t1"} in EXER041 is exactly that object id.

1. A bearer token, stored as a hash

The client sends Authorization: Bearer <token> (RFC 6750). Without a valid one the server answers 401 with WWW-Authenticate: Bearer, which tells the client what it must send.

token = secrets.token_urlsafe(32)                    # 32 random bytes, shown to the user once
store[sha256(token)] = Principal("ana", "customer")  # only the hash is kept

principal = store.get(sha256(presented_token))       # look up the hash of what was sent

A leaked token file contains hashes, not tokens. A plain SHA-256 is enough here because the token is random; a password, which people choose, needs a slow hash. In production the token usually comes from an identity provider (an OAuth access token or a signed JWT) and the service validates it instead of storing it, but the rest of this lesson is the same.

2. The user comes from the credential, never from the body

If the server reads {"user_id": "ana"} from the request, the client can write any user id. The server knows the user only because it validated the token. Ignore every identity field in the body.

3. The user is part of every key

flowchart LR T["Authorization: Bearer …"] --> P["Principal(ana, customer)"] B["body: thread_id = t1"] --> K["key = ana/t1"] P --> K K --> M["conversation memory"] P --> N["notes/ana.json"] P --> F["search filter: no staff documents"]

When the internal key is f"{user_id}/{thread_id}", user B cannot build user A's key: B's t1 becomes ben/t1. That only holds if neither part can contain a separator, so both ids are checked against [A-Za-z0-9_-]{1,64}. The same rule protects the notes file: ../ana as a user id would otherwise be a path.

When B asks for A's thread, answer 404, not 403. A 403 confirms that the thread exists; HTTP explicitly allows a 404 to hide a forbidden resource (RFC 9110, 403 Forbidden).

4. Permission-aware retrieval

Search is a read of company data, and its result goes into the model's context. If a customer's search returns the employee handbook, the model can quote it, and no output filter reliably catches a paraphrase. So the filter goes into the query:

def search_filter(principal):
    if principal.role == "staff":
        return None                                          # everything
    return {"source": {"$nin": ["employee_handbook.pdf"]}}   # a Chroma `where` filter

store.similarity_search(query, k=4, filter=search_filter(principal))

Filtering after the search is weaker in two ways: the forbidden text may already be in a prompt or a trace, and the user gets fewer than k results. Real systems store an access label on every chunk at ingestion (a group, a tenant, a document ACL) and filter on it the same way.

The system prompt is not an access control "Do not reveal the employee handbook to customers" is a request to the model. Lecture 036 showed that requests can be talked around. A document the model never receives cannot leak.

Goal

  1. Explain the difference between authentication and authorization, and where each is checked.
  2. Authenticate requests with a bearer token stored as a hash, and answer 401 correctly.
  3. Derive the user from the credential and bind every conversation and file to it.
  4. Filter retrieval by permission inside the query, before the model sees any text.

Success Criteria

  • Without a valid token every route except the health checks answers 401 with a WWW-Authenticate header
  • A user_id in the request body is ignored: the user comes from the token
  • User B gets 404 for user A's thread, and B's questions with A's thread id go to B's own conversation
  • Thread ids and user ids with / or .. are rejected
  • A customer's search never returns the employee handbook; a staff member's does
  • All 9 checks pass (one is [live API]: it searches the real index)

Walkthrough

  1. bearer_token and authenticate: header names are case-insensitive, and so is the word Bearer.
  2. thread_key and notes_file: validate first, build the key second. For the file, also check the resolved path: two checks, either of which would be enough.
  3. search_filter and permitted_search: one dictionary and one call. The live check runs the same question as a customer and as staff.
  4. route: health routes first (no token), then authenticate, then /ask and /threads/<id>. Return the public thread_id, never the internal key.
  5. Issue two tokens, start the service, and try to read one user's thread with the other user's token.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Authorize tools by role: customers may search and calculate, only staff may use the notes tools. Done when: the same "save a note" request writes a note for a staff member and cannot for a customer, because the customer's assistant never receives the tool.
  2. Connect (EXER028). Store conversations in SQLite so they survive a restart. Done when: after a restart, user A can read and continue their thread and user B still gets 404 for it.

Common Pitfalls

Checking the token and then trusting the body

Authentication passed, so the request "is Ana", and then the code reads data["user_id"]. Every identity the server uses must come from the principal it built itself.

Namespacing without validating

f"{user}/{thread}" with thread = "../ben/t1", or a user id used in a file path, undoes the namespace. Validate ids against an allowlist pattern before they become part of a key or a path.

Filtering retrieved documents after generation

Checking the answer for handbook content is checking for a leak that already happened. Filter in the query.

Authenticating the health checks

The platform calls /healthz without your users' tokens. If it gets a 401, it restarts a healthy container. Keep health routes open and make sure they reveal nothing.

Tokens in logs

An access log that records request headers stores every user's credential. Log the user id, never the header.

Discussion

Why not let the model decide what a user may see, with the role in the system prompt?

Because the model follows instructions from its whole context, including the user's message and retrieved text. Access decisions have to hold even when the model is persuaded otherwise, so they are made in code, before the model receives anything.

A tenant is a company, not a person. What changes?

The key gets one more level (tenant/user/thread), the search filter matches the tenant's documents, and every cache, index and log is partitioned the same way. Lecture 045 adds the tenant to the cache key for this reason.

What would you test before calling this done?

Every route with no token, a wrong token and another user's token; ids with separators; and a retrieval question whose only good answer is in a document the caller may not read. The checks do these.
