Context Engineering

Prompt engineering is about the wording of one prompt. Context engineering is about everything the model reads on a call: what goes in, in what form, in what order, and what it costs.

Overview

Lecture 008 tuned the wording of one prompt, and every call in it had the same, small context. In an agent the prompt is a small part of what the model reads. The rest is tool definitions, conversation history, retrieved documents and tool results, and it changes on every call. Context engineering is deciding what goes into that window and in what form.

You have already done parts of it: trimming history (Lectures 006, 028), choosing chunks to retrieve (019–025), memory strategies (039), separate agents (031). This lecture names the discipline and works through five parts of it on one example: budgeting, long tool results, isolation, position and noise, and measuring.

Concept

The window is a budget

Every call is assembled from sections. All of them are input tokens: you pay for them, they make the call slower, and the model has to read past them to find what matters.

flowchart LR S["System prompt"] --> C["Context of one call"] T["Tool definitions
(sent every call)"] --> C H["History"] --> C R["Tool results"] --> C Q["Question (last)"] --> C C --> M[Model]

The first step is to look at where the tokens go. One order lookup, counted per section:

            system   tools   history   tool_result    total
raw dump        41     193        41        14,475   14,750
compacted       41     193        41         1,730    2,005

The prompt you would tune with Lecture 008 is 41 tokens of a 14,750-token call. In the raw version, 98% of the call is one tool result. Tool definitions are easy to forget: an API sends them with every call, whether or not a tool is used.

A hard budget forces a choice. The simplest choice is to cut whatever does not fit: fill the sections in priority order, keep each one that fits whole, cut the first one that does not, and drop the rest. Cutting is safe for the system prompt, because it comes first, but it is blind about the tool result: it keeps the first orders and loses the later ones, whatever was asked.

Long tool results: compact them

APIs return what their authors needed, not what your model needs. The order API returns warehouse bins, links, weights and every tracking event. Support needs one line per order:

N-5104 | 2026-02-05 | delivered | 12x Barako Bold, 1x Hand Grinder Pro | total 8130 PHP | J&T Express JJ9682283881 | last: Delivered, signed by L. Navarro (Makati)

This is a projection: plain code that keeps the fields you choose. It costs nothing, it is deterministic, and it can be tested offline. The compacted result is an eighth of the raw tokens and answered every question that the raw response answered. The decision about which fields to keep is the engineering: drop the last tracking event and "Why was N-5126 returned?" can no longer be answered.

Isolation: give the raw material to a sub-agent

When you cannot know in advance which fields matter, let a model choose. A sub-agent is a separate call with its own, clean context. It reads the raw response and the question and returns a few lines of findings. The main call sees only the findings:

findings, used = run_subagent(llm, question, raw_response)   # its own call: 14.5k tokens in
sections["tool_result"] = f"Findings from the order lookup: {findings}"   # the main call: ~340 tokens

Isolation does not make the tokens go away. It moves them. The sub-agent still read 14.5k tokens, so for one call the total is slightly higher than the raw dump. Isolation pays off when the main context is re-sent: an agent loop sends its whole history on every step (Lecture 027), so a raw tool result in the history is paid for again on every later step, while the sub-agent paid for it once. Lecture 031's multi-agent teams get the same benefit: each agent's context holds only its own job.

Position and noise

The model does not read a long context evenly. Two research results to know:

  • Lost in the middle (Liu et al., 2023): on multi-document question answering, models did best when the relevant passage was at the start or the end of the context, and noticeably worse when it was in the middle.
  • Context rot (Chroma, 2025): across 18 models, accuracy fell as the input grew, even on simple tasks. It fell faster when the question and the answer shared fewer words, and look-alike distractors made it worse.

Two habits follow, and both are cheap: put the question last, after the long material, and do not add material "just in case". Whether a given amount of noise hurts your model on your task is something to measure, not to assume. The exercise places one fact at the start, in the middle or at the end of up to 1,000 notes about other customers that look like it.

Measure accuracy and tokens together

Every option is a function question → sections, and one loop scores it on the same questions: accuracy, tokens of the main call, and total tokens including any sub-agent. A context strategy earns its place on both axes:

context            accuracy  main tokens  total tokens
raw dump               100%       14,791        14,791
raw, cut to 4000        17%        4,040         4,040     ← fits the budget, loses 5 of 6 answers
compacted              100%        2,046         2,046     ← same answers, 1/7 of the tokens
sub-agent              100%          342        14,900     ← small main call, same total
A bigger window is not a reason to fill it A model that accepts a million tokens still charges for every one, takes longer to answer, and has more to look past. The raw dump and the compacted context gave the same answers here, and one of them cost seven times as much on every call.

The Project

A wholesale customer, Bayani Café, asks about their orders. The order lookup returns account.json: 30 orders, 38 KB, about 14,500 tokens. cases.json holds six questions about the orders, five facts about the café, and 1,000 look-alike notes about other customers. You write the budgeting, compaction, sub-agent, placement and evaluation functions in context_engineering.py; the script builds the context four ways and runs the noise experiment.

Read the last table carefully. On this model, single-fact lookups held at 100% in every position, up to 20,000 tokens of noise: lost-in-the-middle did not show up at this size and on this task. The course's local Ollama model gave the same result when we tried it with up to 24,000 tokens of noise. What did change is the price, 226 times the tokens for the same answer. Run it on a small local model, on a harder question (one that needs two facts at once), or with longer noise, and the accuracy column is where you look for the drop. The point of the experiment is that you know, for your model, instead of guessing.

Goal

  1. Count the tokens of each section of a call and enforce a budget in priority order.
  2. Shrink a large tool result with a projection, and with a sub-agent, and say what each one costs.
  3. Place a fact at different positions among different amounts of noise, and read the result for your model.
  4. Compare ways of building the context on accuracy, main-call tokens and total tokens.

Success Criteria

  • The script prints the tokens of each section for the raw and the compacted context
  • Cutting the raw response to a 4,000-token budget loses the answers about later orders
  • The compacted context answers as well as the raw dump for a fraction of the tokens
  • The sub-agent keeps the main call small, and the table shows that its total tokens did not go down
  • The noise table shows accuracy and tokens for every amount of noise and every position, and you can say what your model's numbers mean
  • All 7 checks pass (6 offline, 1 calls your model)

Walkthrough

  1. Open account.json and read one order. Mark which fields a support agent would ever be asked about.
  2. count_tokens and budget_report: a dictionary in SECTION_ORDER, plus "total".
  3. fit_to_budget: one loop with a left counter. Cut with the tokenizer (encode, slice, decode), not with characters, so the budget is exact. Leave room for CUT_MARKER.
  4. compact_orders: one f-string per order. The check tells you which values a line must contain.
  5. run_subagent: two messages, one call. Count its input and its answer, because that is what it cost.
  6. needle_context: copy the first n distractors, insert the needle. Do not change the list you were given.
  7. evaluate: the loop that produces a row. Keep the main-call tokens and the sub-agent tokens apart: they answer different questions.
  8. Run it. Then change one thing: a budget of 8,000, or drop the last tracking event from the compact line. Does the table move the way you predicted?

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Compact by question: keep only the orders the question names, and fall back to the full compact list when it names none. Done when: the table has a row for it next to compacted, and you can say which question needs the fallback.
  2. Connect (EXER027). An agent loop re-sends its whole history on every step. Count the input tokens of each step of an 8-step loop when the order lookup goes into the history raw, compacted, or through a sub-agent. Done when: the script prints the tokens of every step and the sum for all three, and you can say why the sub-agent's single-call cost is higher but its loop total is lower.

Common Pitfalls

Tuning the prompt while the tool result is 98% of the call

Count the sections first. The biggest section is where the tokens, and usually the problems, are.

Cutting by characters

Characters and tokens differ, most of all in JSON and in languages other than English. A character cut can still overflow the budget. Cut with the tokenizer.

Compacting away the field a question needs

A projection is only as good as its field list. Keep the questions you must answer next to the compaction code, and run them after every change to it.

Reporting only the main-call tokens of a sub-agent

342 tokens looks like a 40-times saving. The total says the sub-agent read the same 14.5k tokens. Report both, and say where the saving really comes from: re-sent context.

Concluding "noise does not matter" from one run

A 100% row says that this model, on this task, at this size, coped. A different model, a question that needs two facts, or a longer context can give a different row. And noise always costs tokens.

Discussion

Is prompt engineering still worth learning?

Yes. The system prompt is still a section of the context, and the techniques of Lecture 008 (clear instructions, delimiters, examples, measuring) still decide how the model uses everything else. Context engineering adds the other sections.

When would you choose a sub-agent over a projection?

A projection when you know which fields matter: it is free, fast and testable. A sub-agent when you cannot know in advance, for example a web page or a log file where the relevant part depends on the question, and when the main context will be re-sent many times.

How do the earlier lectures fit in?

They are context engineering under other names. Retrieval (019–025) selects what goes in. Memory strategies (028, 039) compress history. Multi-agent systems (031) isolate contexts. Long-term memory (028) writes facts outside the window to bring back later.
