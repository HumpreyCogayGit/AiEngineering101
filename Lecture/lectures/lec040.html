Deploying the Capstone

A program on your laptop becomes a service when it takes its configuration from the environment, reports its own health, and runs the same way everywhere.

Overview

The capstone works on your machine: it reads your .env, uses your virtual environment, and you start it by hand. Nobody else can use it yet. This lecture packages it as a container image with a small HTTP API in front of the assistant. The assistant itself does not change: service.py is a third thin shell around Assistant.ask, next to the CLI and the Streamlit app (one core, many interfaces).

The lecture rests on three ideas, none of them specific to AI services: configuration from the environment, health checks, and a reproducible image.

Concept

1. Configuration from the environment

Lecture 001 said "store config in the environment" and used a .env file as a convenience. In deployment the convenience goes away: the platform (Docker, Kubernetes, Azure Container Apps) injects the variables, and no file with secrets is shipped inside the image. An image is copied to registries and laptops; anything in it is published.

from aicourse.settings import settings_from_environment

settings_from_environment()     # real environment variables ONLY; a .env file is ignored
# ConfigError: AZURE_OPENAI_API_KEY: is missing … Set these as environment variables of the running service.

The service checks its configuration at start-up and refuses to start when it is incomplete. A container that cannot work should fail in the first second with a clear message, not on the first customer's question.

2. Health: liveness and readiness

A platform cannot see inside your process. It asks, over HTTP, every few seconds. The two kinds of question below are the ones Kubernetes calls liveness and readiness probes, and other platforms use the same split:

Liveness /healthzReadiness /readyz
QuestionIs the process able to respond at all?Can it serve a request right now?
If it failsThe platform restarts the containerThe platform sends no traffic and waits
Should checkNothing. Return 200Configuration, files and local resources the service needs
Status codes200200 ready, 503 not ready (with the reasons)
Do not call the model in a health check When the provider has a slow minute, every liveness check fails, the platform restarts every container at once, and a slowdown has become an outage. It also costs tokens every few seconds, forever. Health checks test your process, not your dependencies' uptime.
def readiness(checks) -> tuple[int, dict]:
    results = {}
    for name, check in checks.items():
        try:
            check(); results[name] = "ok"
        except Exception as exc:                 # report the problem, never crash
            results[name] = f"{type(exc).__name__}: {exc}"
    ready = all(v == "ok" for v in results.values())
    return (200 if ready else 503), {"status": "ready" if ready else "not ready", "checks": results}

A .dockerignore is the second lock on the same door: .env, .venv/, .chroma/ and .git/ are not even sent to the builder.

The routes as a function

route(method, path, body, ask) -> (status, json) contains every decision of the API and no sockets, so the checks call it directly. The few lines that speak HTTP are given. When the assistant raises, the caller gets a plain 500 and the traceback goes to the log: error text can contain keys, URLs and internal names.

The Project

You complete service.py (port, configuration check, liveness, readiness, routes), the Dockerfile and its .dockerignore. Then you build the image, run it with your configuration injected, and ask it a question.

Sample run

$ docker build -f EXER040/solution/Dockerfile -t nimbus-helpdesk .
$ docker run --rm nimbus-helpdesk                           # no configuration: it refuses to start
ERROR helpdesk: Course configuration problem:
  - AZURE_OPENAI_ENDPOINT: is missing
  - AZURE_OPENAI_API_KEY: is missing
  - AZURE_OPENAI_CHAT_DEPLOYMENT: is missing

Goal

  1. Configure a service from environment variables only, and fail fast when they are missing.
  2. Implement liveness and readiness endpoints, and explain what each must not check.
  3. Write a Dockerfile that installs locked dependencies, runs as a non-root user and declares a health check.
  4. Keep secrets out of the image and out of error responses.

Success Criteria

  • The service refuses to start, naming the missing variables, when the environment is empty
  • /healthz answers 200, and /readyz answers 503 with the reason when a check fails
  • Two questions with the same thread_id share a conversation
  • The image builds, the container answers a question, and docker ps shows it as (healthy)
  • There is no .env in the image, and whoami inside the container is not root
  • All 12 checks pass (offline; they do not need Docker)

Walkthrough

  1. service_port, check_config, liveness: a few lines each. Run the checks after each one.
  2. readiness: run every check, even after one failed, so the response lists everything that is wrong.
  3. route: handle the two health routes first, then /ask with its 400, 405 and 500 cases.
  4. Start the service without Docker: set -a; source .env; set +a, then run service.py and use curl.
  5. Complete the Dockerfile step by step. check.py reads it as text, so you get feedback without building.
  6. Build, run, and check the three things a reviewer would: docker ps (healthy), whoami (not root), ls -a /app (no .env).

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Add a readiness check for the vector index, and build the index in a warm-up thread at start. Done when: /readyz answers 503 until the index exists and 200 afterwards, while /healthz stays 200.
  2. Connect (EXER035). Write one structured JSON log line per question, and add a GET /stats route with running totals. Done when: each question logs thread, seconds, tokens and tools (never the question text), and /stats returns the totals.

Reference code, for after you have tried: EXER040/stretch/

Common Pitfalls

COPY . .

It copies .env, .git and your local index into the image unless a .dockerignore stops it, and a missing ignore line is silent. Copy what you need, by name.

Secrets in ENV or ARG

They are stored in the image's history and visible to anyone who pulls it. Pass secrets when the container starts (--env-file, the platform's secret store), never when the image is built.

Listening on 127.0.0.1

Inside a container, localhost is the container itself. A service bound to 127.0.0.1 works in the health check and is unreachable from outside. Bind to 0.0.0.0.

Quotes in .env with --env-file

Docker passes each line as written: KEY="abc" gives the value "abc" with the quotes. Write KEY=abc, as Lecture 001 recommended.

State inside the container

Conversations (InMemorySaver), notes and the vector index live in the container and vanish with it. Two replicas do not share them either. Real deployments move state out: a database checkpointer (Lecture 028) and a volume or a managed vector store.

Discussion

What is still missing before real customers could use this?

Authentication on /ask, rate limiting, HTTPS (usually from the platform), persistent state, a request timeout, structured logs and metrics, and a pipeline that runs the capstone evaluation before every release. The image is the unit all of those are built around.

Why a hand-written HTTP server instead of a web framework?

To keep the lecture about deployment and the dependencies unchanged. In a real project you would use a framework such as FastAPI for validation, async handlers and generated API docs. route() would become three small handler functions; nothing else in this lecture changes.

The first question to a new container is slow. Why, and what would you do?

The knowledge base is embedded and indexed on first use. Build the index at start-up and report "not ready" until it exists (stretch goal 1), bake it into the image, or use a shared vector store.
