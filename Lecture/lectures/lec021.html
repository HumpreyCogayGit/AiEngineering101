Vector Store with Chroma

A vector store is a database built for one query: "find the records nearest to this vector". Chroma runs it locally with no server and no cost.

Overview

In Lecture 019 you compared a query with every vector in a Python list. That doesn't scale and doesn't survive a restart. A vector store persists (id, vector, text, metadata) records and finds nearest neighbours quickly with an index. We use Chroma embedded in our Python process, storing to .chroma/.

Approximate nearest neighbours

Comparing with every vector is O(n). Chroma builds an HNSW index (Hierarchical Navigable Small World: layers of graphs that link each vector to its near neighbours; Malkov and Yashunin, 2016). A search walks the graph from a coarse layer to a fine one and finds approximately the closest vectors: it can occasionally miss a true nearest neighbour, and in exchange its search time grows roughly with the logarithm of the collection size instead of linearly. We set the distance to cosine, so smaller distance = more similar (distance = 1 − similarity).

Using it through LangChain

client = chromadb.PersistentClient(path=".chroma", settings=chromadb.Settings(anonymized_telemetry=False))
store = Chroma(client=client, collection_name="exer021_kb", embedding_function=get_embeddings(),
               collection_metadata={"hnsw:space": "cosine"})

store.add_documents(chunks, ids=ids)                               # embeds + stores
store.similarity_search_with_score("Can I bring my dog?", k=3)     # [(Document, distance), ...]
store.similarity_search("delivery time", k=2, filter={"source": "shipping.md"})
retriever = store.as_retriever(search_kwargs={"k": 4})            # a Runnable for chains (Lecture 022)

Idempotent ingestion

Ingestion scripts get run again and again. With random ids, each run duplicates every chunk, and your top-k fills up with copies. With content-based ids (a hash of source + text), the same chunk always gets the same id, so you can skip what's already stored and re-runs change nothing.

hashlib.sha256(f"{source}::{text}".encode()).hexdigest()[:32]

Worked example: what is stored, and what a search returns

Ingest. The knowledge base becomes 19 chunks. One stored record looks like this:

id        58dafe0e4c007383e1b2ea89204cde0c            sha256("brewing_guide.md::# Brewing Guide …")[:32]
embedding 1536 floats
document  "# Brewing Guide\n\n## Pour-over\n\nUse **15 g of coffee to 250 ml of water** …"
metadata  {"source": "brewing_guide.md", "chunk_id": 0}
first run : Added 19 new chunks; collection now has 19 chunks
second run: Added  0 new chunks; collection now has 19 chunks

The second run computed the same 19 ids, asked the store which of them exist (store.get(ids=ids)), got all 19 back, and added nothing. It also embedded nothing: no API call was made for chunks that were already there.

Search. "How much is express delivery?" is embedded and compared with the stored vectors:

distance  similarity  source              chunk  starts with
0.600     0.400       shipping.md         18     ## Shipping fees — Standard shipping is **free for orders over ₱1,500** …
0.634     0.366       shipping.md         17     # Shipping Information — ## Where we ship …
0.749     0.251       loyalty_program.md  10     ## Tiers — … **Gold** … free express shipping …

Chroma returns the first column. The second is 1 − distance, the cosine similarity of Lecture 019. The best result has the smallest distance: sort the wrong way round and you would put the loyalty tiers first.

The third result is a good example of similar-but-not-relevant: the Gold tier mentions "free express shipping", which is close in meaning to the question and does not answer it. With k=2 it would not have been returned. That is the argument for a small k, and for the evaluation in Lecture 024.

The same search with a filter, filter={"source": "loyalty_program.md"}:

0.749     loyalty_program.md  10     ## Tiers …
0.818     loyalty_program.md   9     # Nimbus Rewards (Loyalty Program) …

The distances did not change: chunk 10 is still at 0.749. A filter does not make anything more similar, it only removes candidates before the ranking. Used well ("only this customer's documents"), that is exactly what you want. Used on the wrong file, as here, it guarantees a confident-looking list of the wrong passages, with nothing to warn you.

Goal

  1. Explain what a vector store stores and how approximate nearest-neighbour search works.
  2. Create a persistent Chroma collection and search it with scores and filters.
  3. Make ingestion idempotent with content-based ids.

Success Criteria

Walkthrough

  1. Most checks use DeterministicFakeEmbedding in a temporary folder: fast, free and offline.
  2. store.get(ids=ids)["ids"] returns only the ids that exist, which is how you find what's new.
  3. Run the script twice and compare the counts.
  4. From Lecture 022 on, aicourse.rag.get_vector_store() wraps all of this.

Common Pitfalls

Distance vs similarity

Chroma returns distances: lower is better. Some other stores return similarity scores, where higher is better. Check before you sort or set thresholds.

Stale collections after changing models

Changing the embedding model requires a new collection, or Chroma rejects vectors of a different dimension.

Deleting the wrong folder

.chroma/ is a cache you can rebuild from your documents. Never keep the only copy of data in it.

Discussion

How would you handle a document that was edited?

Its chunks get new content-based ids. Delete the old chunks by source metadata, then add the new ones. Unchanged chunks keep their ids and aren't re-embedded.

When is a vector store overkill?

A few hundred chunks fit in memory with NumPy, as in Lecture 019. Persistence, filters and scale are what justify a database.
