Human in the Loop

Some actions are too consequential to automate fully. Pause the agent, show a person what it's about to do, and continue with their decision, even hours later.

Overview

Sending emails, issuing refunds and deleting data: agents that act need oversight. In Lecture 018 you asked for approval with input(), which blocks a process and only works in a terminal. LangGraph's interrupt() pauses a graph, saves it with the checkpointer, and returns control to your app (web UI, Slack, email). Command(resume=...) continues it later.

result = graph.invoke({"messages": [...]}, config)
result["__interrupt__"][0].value          # what the human should see
graph.invoke(Command(resume={"action": "approve"}), config)   # same thread_id
How resume works On resume, LangGraph re-runs the interrupted node from the start, and this time interrupt() returns the human's value instead of pausing. So code before interrupt() in that node must be safe to run twice: no side effects before the interrupt.

Approve, edit, reject

DecisionGraph does
approveCommand(goto="tools"): run the calls as proposed
editReplace the AI message (same id, so the reducer overwrites it) with corrected arguments, then run tools
rejectAdd a ToolMessage per call ("not executed: …reason") and go back to the agent, which can apologise or try another approach

A node can return Command(goto=..., update=...) to route and update state at once. Declare its possible destinations with add_node(..., destinations=("tools", "agent")) so the graph diagram stays correct.

Only risky tools need a gate

Reading the inbox happens freely; send_email and refund_order wait for a person. Gate by consequence: if a mistake would be expensive, embarrassing or irreversible, ask first.

Row 1. The first four messages are: your request, the model asking for read_inbox, the inbox as a tool message, and the model asking for two emails. read_inbox ran without a question because it is not in RISKY: review returned Command(goto="tools") straight away. The second time, review reached interrupt(). The state was saved with next = review, and start() returned with the two proposed emails in __interrupt__. Nothing has been sent, and the process could exit here.

Row 2. The reject decision made the review node run again from its first line. This time interrupt() returned the decision instead of pausing. The node added two tool messages, one per rejected call:

ToolMessage  Not executed: a human rejected this action (tone too formal, try again shorter).   ×2

and routed back to agent. The model read the reason and proposed two new, shorter emails. Carla's draft changed from "I'm sorry your Hand Grinder Pro arrived…" to "Sorry about the cracked handle! We'll r…". That put the graph in review again, at a second interrupt. Three messages were added (T T A), and still nothing was sent.

Row 3. Approve: review re-ran, interrupt() returned {"action": "approve"}, and the node routed to tools. Two emails were sent (T T), the model wrote its summary (A), and next is empty: the run is over.

Two things in this table are easy to miss. The reason you typed is not a log entry: it is a message the model reads, which makes a rejection a way to steer the agent, not only to stop it. And every tool call in the list has an answer: the two rejected calls got "Not executed" messages. Leave those out and the next model call fails, because the history would contain calls nobody answered.

Goal

  1. Pause a graph with interrupt() and resume it with Command(resume=...).
  2. Implement approve, edit and reject flows.
  3. Use Command(goto, update) for routing from inside a node.
  4. Decide which actions need human approval.

Success Criteria

  • Reading the inbox happens without asking
  • Every email and refund waits for your decision
  • Approve, edit and reject each behave correctly
  • All 5 checks pass (offline)

Walkthrough

  1. pending and resume are one-liners; do them first.
  2. In review, return early with Command(goto="tools") when no call is risky.
  3. For edit, build new tool calls with {**call, "args": new_args} and keep id=last.id on the new AIMessage.
  4. Run it and reject the refund with a reason. Read how the agent responds.

Stretch goals

Optional, for when the checks pass. Neither goal is needed for "complete", and the checks must still pass afterwards.

  1. Extend. Require approval only for refunds above a threshold. Done when: a ₱200 refund runs without a pause, and a ₱3,450 refund waits for a decision.
  2. Connect (EXER028). Persist the pending approval so that the script can be closed and resumed. Done when: start exits while waiting, and approve in a new process finishes the same run.

Reference code, for after you have tried: EXER029/stretch/

Common Pitfalls

No checkpointer

interrupt() needs saved state to resume from. Compile with a checkpointer and reuse the same thread_id.

Side effects before interrupt()

They run twice (once before pausing, once on resume). Put side effects after the interrupt, or in a separate node.

Unanswered tool calls after reject

Every tool call needs a matching tool message, or the next model call fails. Add a rejection message for each.

Discussion

Doesn't approval defeat the point of automation?

Not if the agent does 95% of the work (reading, deciding, drafting) and the human spends 5 seconds approving. As trust grows from logged approvals, you can auto-approve low-risk cases.

What should the approval screen show?

The exact action, its arguments in readable form, and why the agent wants to do it. "Approve tool call?" with raw JSON invites rubber-stamping.
