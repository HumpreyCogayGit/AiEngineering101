Caching and Batch Work

Three ways to pay less for the same answers: store them, let the provider reuse your prompt, or ask for them later. Each one can serve a wrong answer if you are careless.

Overview

Lecture 035 measured what each question costs. Most of the cost is input tokens: the retrieved documents and the system prompt, sent again with every question. Many questions repeat ("Is shipping free?"), and much of every prompt repeats too. This lesson removes some of that repetition at three levels, and is careful about what each level may and may not do.

Concept

1. A response cache, and what goes into its key

An exact-match cache returns the stored reply when the same question arrives again. The danger is in the word "same". The answer depends on more than the question:

cache_key(question,
          model=...,            # a new model answers differently
          prompt_version=...,   # so does a new system prompt
          tools=...,            # or a new tool set
          policy_version=...,   # or new guardrails, or new documents (stretch goal 1)
          tenant=...,           # company A's answer must never reach company B
          role=...)             # staff search staff-only documents (Lecture 042)

Leave one out and the cache serves answers from before the change. Leave out the tenant or role and it serves answers across a boundary that Lecture 042 just built. The question itself is normalized (case, spacing, trailing punctuation), and the whole key is hashed, because keys end up in logs.

Some replies must never be stored:

  • Follow-up turns. "And to Cebu?" means something different in every conversation.
  • Answers that changed something. Replaying "I saved your note" saves nothing.
  • Blocked replies. The guardrails are cheap; run them every time.

Entries also expire (a time to live). The TTL bounds how long a wrong answer can live; it does not prevent one.

Why not a semantic cache?

A semantic cache matches questions by embedding similarity, so "Do you ship for free?" hits the entry for "Is shipping free?". The check in this exercise measures why that is dangerous, with the course's embedding model:

different answers   unopened vs opened beans (30 vs 14 days)   0.963
                    express vs standard shipping to Cebu        0.900
same answer         "Is shipping free?" / "Do you ship for free?"  0.840

The pair with different answers is more similar than the paraphrase. Any threshold low enough to accept the paraphrase also returns the 30-day answer to someone who opened the bag. Embeddings measure topic, not the one word that changes the policy.

2. Prompt-prefix caching at the provider

When the beginning of a prompt is identical to a recent one, providers that support prompt caching reuse the processing of that prefix and charge less for it, usually only above a minimum length (1,024 tokens on several providers). They report it in usage.prompt_tokens_details.cached_tokens. Your job is the layout: static first, volatile last.

$ uv run python EXER045/solution/prefix_experiment.py
unstable  call 1: prompt  1806 tokens, cached     0
unstable  call 2: prompt  1806 tokens, cached     0      ← the time is the first line: every prompt differs
stable    call 1: prompt  1805 tokens, cached     0
stable    call 2: prompt  1805 tokens, cached  1771      ← documents first, name and time last
stable    call 3: prompt  1805 tokens, cached  1771

Where the prefix can end depends on the provider. On the deployment used to write this lesson, reuse stopped at the end of an identical system message: the same 2,000 tokens of order data in the user message were not reused when only the question after them changed, and were reused once moved into the system message (stretch goal 2). Measure on your provider before rearranging prompts for a cache.

Not every provider reports it A local Ollama keeps the processed prompt of its last request and reuses a shared prefix, but reports no cached tokens. Compare latencies there instead.

3. Batch endpoints for work nobody waits for

Evaluation runs, re-scoring a dataset, summarizing yesterday's tickets: nobody is waiting for these answers. Several providers accept a file of requests and return the results within a day for about half the normal price (Azure and OpenAI both document it). The file is one JSON request per line:

{"custom_id": "q-0003", "method": "POST", "url": "/v1/chat/completions",
 "body": {"model": "...", "messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "Is shipping free?"}]}}

Results can come back in any order; custom_id is how you match them. Submitting the file is provider-specific and not every provider offers it (Ollama does not), so the exercise builds the file and stops there.

Goal

  1. Build a cache key from everything an answer depends on, including tenant and role.
  2. Decide which replies may be cached, and expire the rest.
  3. Explain why similarity-based caching serves wrong answers.
  4. Lay out prompts so a provider can reuse their prefix, and measure whether it does.
  5. Package offline work for a batch endpoint.

Success Criteria

  • The cache key changes when the model, prompt version, tools, policy, tenant or role changes, and not for case, spacing or trailing punctuation
  • Expired entries are removed and counted; hits, misses and the hit rate are reported
  • Blocked replies, follow-up turns and answers that saved something are never cached
  • Two customers on two days send prompts that are identical up to the volatile part
  • prefix_experiment.py shows cached prompt tokens for the stable layout from the second call on (on a provider that reports them)
  • All 8 checks pass (one is [live API]: it shows with your embedding model why a semantic cache is unsafe)

Walkthrough

  1. normalize and cache_key: json.dumps(..., sort_keys=True) makes the same dictionary give the same text, then hash it.
  2. ResponseCache.get: an expired entry is deleted and counted before it is reported as a miss.
  3. cacheable: four rules, each one a sentence in the Concept section.
  4. build_messages: documents in the system message; name, date and question in the user message.
  5. batch_lines: one json.dumps per question, no newlines inside a line.
  6. Run caching.py and prefix_experiment.py, then the live check, and look at the similarity numbers your embedding model gives.

Common Pitfalls

A key without the tenant or role

The cache becomes a way around every access rule in Lecture 042. The first staff member's answer, from the handbook, is served to every customer who asks the same question.

Caching answers to follow-up questions

"How much is it?" has a different answer in every conversation. Cache only first turns, or include a hash of the conversation in the key (which makes hits rare anyway).

A timestamp at the top of the system prompt

"Today is 2026-11-15 14:03:22" as the first line makes every prompt unique from token one, and the provider can reuse nothing. Put the date last, and only to the day if that is all the model needs.

Measuring a cache with repeated prompts

Sending the same prompt twice measures whole-prompt reuse, not prefix reuse. Make each test question unique (stretch goal 2 adds a random reference) or the numbers flatter the layout.

A batch job for something a user waits for

Batch results arrive within hours. Use it for evaluations and bulk jobs only.

Discussion

The hit rate is 3%. Is the cache worth it?

Measure the questions first: a support desk often has a few questions that make up a large share of the traffic, and those are the ones worth caching. If the traffic is all long, personal conversations, a response cache saves little; prefix caching still helps every call.

How would you share the cache between three replicas?

Move it to a shared store such as Redis, with the same key and a TTL set on each entry. The rules for what may be cached do not change.

A document changes. What has to happen, in which order?

Re-index the document, then change the knowledge-base version in the key in the same deploy. Old entries stop matching at once, and the first question after the change pays for one fresh answer.
